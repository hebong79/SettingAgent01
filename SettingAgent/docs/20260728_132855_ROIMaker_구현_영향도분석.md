## 3. 핵심 설계 — 왜 새 라우트를 만들었나 (라이브 대조 실험)

같은 DB·같은 편집에 대해 두 경로를 실제로 실행한 결과:

```
[신규] POST /capture/slots/sync-roi
  실행 전: 24행 · 센터링 23 · vpd 23 · 점유 23
  실행 후: 24행 · 센터링 23 · vpd 23 · 점유 23     ← 기하만 갱신
  결과: updates 2 · inserts 1 · unchanged 21 · orphans 0

[기존] POST /capture/slots/load-roi
  실행 전: 24행 · 센터링 23 · vpd 23 · 점유 23
  실행 후: 24행 · 센터링  0 · vpd  0 · 점유  0     ← ★ 전량 소실
```

`load-roi` 는 `replaceSlotSetup`(DELETE+INSERT 전량)을 쓴다. ROI 손보정은 **일상 조작**이므로 그릴 때마다
정밀수집 결과가 날아가면 워크플로가 성립하지 않는다. 기존 "전체 재적재" 버튼은 그대로 두고, ROIMaker 는
**차등 동기만** 탄다(정적 봉인 테스트가 이를 소스 수준에서 고정한다).

### 차등 규칙

| 상태 | 동작 |
|---|---|
| 양쪽 존재 · 기하 상이 | `slot_roi` + `updated_at` 만 UPDATE(타 컬럼 무접촉) |
| 양쪽 존재 · `slot_id` 불일치 | **전량 중단** + 409(아이덴티티 붕괴 상태에서 쓰기 금지) |
| 파일에만 존재 | INSERT(enrichment 전부 NULL) |
| DB 에만 존재 | **삭제하지 않고** `orphans[]` 로 보고 |
| 파일 없음/파싱 실패/주차면 0 | 무변경 + `ok:false` |

## 4. 라이브 검증에서 **발견해 고친 결함 2건**

설계대로 짜고 유닛테스트가 전부 green 이었는데, 실제 서버·실제 정본 파일에 붙이니 둘 다 실패했다.
**둘 다 유닛테스트로는 잡을 수 없었다** — 픽스처가 내 가정대로 생겼기 때문이다.

### 결함 A — 정본 파일은 전역 idx 를 쓰지 않는다

- **증상**: 신규 주차면 저장 후 `sync-roi` 가 `slot_id 아이덴티티 불일치 16건` 으로 거부.
- **원인**: 실 `data/Place01/PtzCamRoi.json` 은 **프리셋마다 idx 가 1 부터 다시 시작**한다
  (`cam1:preset2 idx 1`, `cam1:preset3 idx 1` …). 설계는 "파일 idx = 전역 1..N 순열"을 전제했다.
  로드 시 `normalizeGlobalIdx` 가 전역번호를 재부여하므로 **메모리 버퍼가 파일과 전 프리셋에서 다르고**,
  변경 프리셋만 저장하면 파일이 "일부 전역·일부 프리셋별" 혼합이 되어 다음 로드에서 번호가 또 밀린다.
- **수정**: `markAllDirty()` 신규 — 로드 시 재부여가 일어났으면 **전 프리셋을 저장 대상**으로 잡아
  첫 저장에서 파일을 전역번호로 **수렴**시킨다. (`roimakerCore.js`, 회귀 테스트 1건 추가)
- **평가**: 아이덴티티 가드가 **DB 파괴 대신 409 로 거부**했다. 가드가 없었으면 16개 슬롯의 기하가
  엉뚱한 slot_id 에 붙었을 것이다 — 조용히.

### 결함 B — 무결성 가드가 자기 저장을 막았다

- **증상**: 새 주차면 1개 추가 후 저장 → `409 expected:8 actual:7`.
- **원인**: `expectRawCount` 를 **현재 버퍼 길이**로 보냈다. 방금 추가한 1건 때문에 8이 됐는데 파일은 7이다.
- **수정**: `baseCounts` 를 로드 시점에 기록해 **로드 시점 개수**를 보낸다. 가드의 본래 의미
  ("내가 읽은 뒤로 파일이 바뀌지 않았는가")와 일치한다. (`roimakerCore.js`, 회귀 테스트 1건 추가)

## 7. 운영 유의사항

1. **하드리로드 필수** — `web/*` 는 nodemon 감시 밖이다. 기존 탭은 Ctrl+Shift+R 전까지 옛 JS 로 돈다.
2. **DB 부트스트랩 선행** — `sync-roi` 는 `place_info`/`camera_info`/`preset_info` 부모가 있어야 INSERT 할 수 있다.
   완전히 빈 DB 에서 처음 호출하면 `FOREIGN KEY constraint failed` 로 **거부**(DB 무변경)된다.
   최초 1회는 기존 **"ROI 로딩"(load-roi)** 버튼으로 부모를 만든 뒤 ROIMaker 를 쓴다.
3. **첫 저장은 전 프리셋 쓰기** — 정본이 프리셋별 번호를 쓰고 있으면(현재 실 파일이 그렇다) 첫 저장에서
   5개 프리셋이 함께 기록된다. 화면 메시지로 안내된다. 이후 저장은 변경 프리셋만.
4. **전체 보기의 타 프리셋 ROI 는 위치가 맞지 않는다** — 좌표계가 프리셋별이라 원리적으로 그렇다.
   흐린 점선 + `(타 프리셋)` 라벨 + 편집 불가로 표시한다.
5. **제어탭 `#place-delete`(주차면 행 삭제)와 병용 주의** — 그쪽은 행을 지워 전역번호 재부여를 유발한다.
   그 뒤 ROIMaker 로 오면 저장 시 `sync-roi` 가 409 로 막을 수 있다(그때는 load-roi 로 재적재).

## 8. 미검증 · 한계 (위장 없음)

1. **브라우저 실렌더 미확인** — 이 저장소엔 DOM 자동화가 없다. 신규 `web/` 코드 **약 1,060줄**이
   육안 검증 대상이다. 순수 로직(26케이스)과 DOM 계약(16케이스 정적 봉인)으로 최대한 덮었지만,
   **실제 마우스 제스처·고무줄·정점 드래그·토글 색상·목록 렌더는 마스터 확인이 필요**하다.
   (메모 기록상 이 미검증 면적은 7라운드째 누적 중이다.)
2. **실카메라 미검증** — 라이브 확인은 Unity 시뮬레이터 소스로만 했다. 실카(RTSP) 프레임 고정
   (`freezeFrame`)이 MJPEG 가 아닌 경로에서도 되는지는 확인하지 않았다.
