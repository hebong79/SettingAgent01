## 3. 핵심 설계 결정

### 3-1. RPC 는 로직을 갖지 않는다

메서드는 둘 중 하나로만 실행된다.

- **`http`** — 기존 REST 라우트로 `app.inject()` 위임(인메모리, 네트워크 0). 55 메서드.
- **`handler`** — REST 에 **대응 라우트가 없는** 승격 기능만. 15 메서드.

`test/rpcParity.test.ts` 가 이를 두 방향으로 고정한다: ① 같은 작업의 REST 결과와 RPC 결과가 **바이트 동일**(`place.save` 후 파일 md5 비교) ② 모든 브리지 메서드의 위임 URL 이 기존 라우트 경로 집합 안에 있는지 정적 검사(새 경로를 만들면 실패).

### 3-2. BUSY 와 CONFLICT 를 갈랐다

HTTP 409 하나에 섞여 있던 두 상황을 분리했다. 외부 제어자의 재시도 정책이 여기서 갈린다.

| 코드 | 상황 | 판정 근거(기존 라우트 문자열 재사용) | 대응 |
|---|---|---|---|
| `-32001 BUSY` | 잡 점유 | `pipeline busy` · `still running` · `already running` · `busy` | 백오프 재시도 |
| `-32005 CONFLICT` | 무결성 가드 거부(**파일·DB 무변경**) | 그 외 전부(개수 불일치·slot_id 불일치·G1~G4 거부) | 사람 개입 |

판정 불가 시 **CONFLICT** 로 둔다 — 무한 재시도보다 안전하다.

같은 이유로 404 도 갈랐다: Fastify **라우트 미등록**(기능이 꺼져 있음) → `-32004 UNAVAILABLE`, 핸들러 본문 404(값이 없음) → `-32002 NOT_FOUND`.

### 3-3. 파괴적 메서드는 `confirm` 없이 위임되지 않는다

`slot.roi.load` · `slot.reset` · `capture.finalize` · `grid.apply` · `place.preset.clear` 는 RPC 계층에서 `confirm:true` 를 요구한다. 이 게이트 필드는 하류 라우트로 새지 않는다(`omit`).

특히 `slot.roi.load` 는 카탈로그 note 에 실측치를 적었다 — *"⚠ 검출·점유·센터링이 초기화된다(실측 23→0). 빈 DB 부트스트랩에만 쓰고, 이후에는 `slot.roi.sync` 를 써라."*

### 3-4. 두 삭제 규약을 둘 다 살렸다

저장소에 실제로 두 UI 가 서로 다른 삭제 규약을 쓰고 있다. 어느 쪽도 임의로 바꾸지 않고 **파라미터로 노출**했다.

| mode | 동작 | 위험 | 기본값 |
|---|---|---|---|
| `clear` | `points: []` 로 기하만 비움, 전역번호 보존 | 없음 — DB slot_id 재매핑 위험 원천 제거 | ✅ |
| `remove` | 엔트리 제거 + 남은 전부 1..N 재압축 | 전역번호 변경 → DB 재구성 필요 | 응답 `issues[]` 에 경고 동반 |

`remove` 시에는 **전 프리셋을 함께 기록**한다(한 프리셋만 쓰면 파일이 혼합번호가 되어 다음 로드에서 번호가 밀린다 — 2026-07-28 ROIMaker `markAllDirty` 교훈).

### 3-5. 카메라 점유 판정처를 하나로

기존에는 `lensCalib.isBusy` 클로저가 **렌즈 잡 시작 거부에만** 쓰였다. 이를 이름 붙여 추출해 RPC 의 `requiresCamera` 게이트와 공유한다. RPC 용(`rpcBusy`)은 여기에 렌즈 잡 자신을 더한다 — 렌즈 잡에 그걸 주면 자기 상태 때문에 영원히 시작 못 하므로 확장은 RPC 쪽에만 준다.

## 5. 검증

### 5-1. 유닛테스트

```
tsc --noEmit                 0 오류
신규 4파일                    92 green
전체                          3232 green / 2 failed (사전 존재 — 아래)
```

**구현 중 테스트가 잡은 실제 결함 2건**

1. **본문 없는 POST 위임이 전부 400 이었다.** 브리지가 `content-type: application/json` 을 항상 붙여 Fastify 가 `FST_ERR_CTP_EMPTY_JSON_BODY` 로 거부했다 — 라우트는 정상인데 브리지 때문에 실패하는 거짓 오류. → 본문이 있을 때만 헤더를 붙이도록 수정, 테스트로 고정.
2. **`cam.preset.list` 가 헤드리스에서 죽었다.** `GET /viewer/api/camerapos` 로 위임했는데 그 라우트는 `viewer.enabled && sources` 일 때만 등록된다. → 파일 정본을 직접 읽는 서비스로 전환(upsert/delete 와 같은 소스).

### 회귀 위험이 낮은 이유

1. 모든 신규 코드가 **새 파일**에 있다(`src/rpc/`, `src/capture/placeRoiEdit.ts`).

3. RPC 라우트는 항상 등록되지만, 개별 메서드는 주입된 deps 로 가용성이 판정된다(미배선 → 카탈로그 `available:false` + 호출 시 `-32004`).

| Q2 | `points: []` vs "4점 필수" 테스트 모순 | 미해소(사전 존재) | 규약(비우기)이 맞다면 두 테스트의 불변식을 수정 |
| Q3 | 미구현 승격 3건 | 문서화 완료 | 필요해질 때 착수 |
| Q4 | 웹 클라이언트를 `/rpc` 로 이관할지 | 현행 REST 유지 | 회귀 위험 대비 이득이 작아 **유지 권장**. 신규 기능만 RPC |
| Q5 | 카탈로그 → MCP 도구 자동 노출 | 미착수 | 카탈로그 스키마가 이미 그 형태다 |

## 8. 사용 예 (외부 제어자)

```bash
# 1) 무엇을 할 수 있는지 묻는다
curl -s http://localhost:13020/rpc/catalog

# 2) 주차면 하나 추가 (idx 는 서버가 부여)
curl -s -X POST http://localhost:13020/rpc -H 'content-type: application/json' -d '{
  "jsonrpc":"2.0","id":1,"method":"place.space.add",
  "params":{"camId":1,"presetIdx":1,"points":[{"x":0.8,"y":0.8},{"x":0.9,"y":0.8},{"x":0.9,"y":0.9},{"x":0.8,"y":0.9}]}}'

# 3) 실수했으면 되돌린다
curl -s -X POST http://localhost:13020/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"place.backups"}'
curl -s -X POST http://localhost:13020/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":3,"method":"place.revert","params":{"backupFile":"PtzCamRoi.20260728T101432Z.bak.json"}}'

# 4) 번호판 하나 골라 슬롯에 붙이고 센터라이징
curl -s -X POST http://localhost:13020/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":4,"method":"plate.pickAt","params":{"cam":1,"preset":1,"point":{"x":0.52,"y":0.48}}}'

# 5) 시뮬레이터도 같은 평면에서
curl -s -X POST http://localhost:13020/rpc -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":5,"method":"unity.cam.list","params":{}}'
```
