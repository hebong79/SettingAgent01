## 1. 배경과 목표

지금까지 SettingAgent 는 "웹(`web/*.js`)이 계산하고, 서버는 파일·DB I/O 만 한다"는 지점이 여러 곳 남아 있었다.
문제는 웹이 곧 브라우저이고, 브라우저는:

- **셸이 없다** — 외부 제어자(RPC 클라이언트, MCP, 자동화 스크립트)가 브라우저를 띄우지 않고는 이 로직을 재사용할 수 없다.
- **헤드리스 검증이 안 된다** — vitest 로 값의 정확성은 볼 수 있어도(웹 파일을 import 해서), 실제 서버 계약(REST/RPC)으로는 이 기능이 노출돼 있지 않다.

이번 작업은 리더가 우선순위를 지정한 4건(**① 인증 토큰 ② 투어링(순회) ③ 점유판정 ④ 슬롯편집**)을
"서버가 정본을 갖고, 웹은 서버를 호출하는 껍데기"로 승격한다. 4건 모두 **결정형 도구**(수치반복·규칙연산)로,
LLM 판단이 개입할 지점이 없다는 것을 설계 단계에서 확인했다(`AgentRuntime.judgeOccupancy` 는 점유"율" 요약
자문이지 슬롯 판정이 아니며, 이번 `slot.occupancy.evaluate` 와 무관하다).

작업은 리더가 정한 순서(**토큰 → 투어링 → 점유판정 → 슬롯편집**)로 4개 웨이브(W1~W4)로 나눠 순차 실행했다.
각 웨이브는 독립 커밋 가능 단위이며, 끝날 때마다 `npx tsc --noEmit` 0 + 관련 vitest green 을 확인한 뒤 다음으로 넘어갔다.

## 2. 4건 각각 — 무엇이 웹에만 있었고, 무엇을 서버로 옮겼는가

### 2-1. W1 — 인증 토큰

**웹에만 있던 것**: 토큰을 실제로 붙여 보내는 코드(`tokenHeaders()` app.js:4464, 사용처 4곳뿐)와 토큰을 화면 입력칸에 담아두는 상태(`#viewer-token`, 새로고침 시 소실).

**서버에 있었지만 반쪽이던 것**: RPC 게이트(`dispatch.ts` `tokenGate`)는 카탈로그의 `mutating` 기준으로 이미 제대로 동작했다. 그러나 `/viewer/api/*` 4개 라우트에만 인라인 토큰 검사가 있었고, `/capture/*`·`/calibrate/*`·`/discover/*`·`/mapping*`·`PUT /settings` 는 토큰을 켜도 무인증으로 뚫려 있었다.

**결정적 사실(작업 착수 전 조사)**: 토큰을 켜는 순간 웹 UI 의 변이 요청 35곳 중 31곳이 토큰을 안 보내 403 으로 죽는다. 그래서 "게이트를 넓히는 일"(서버)과 "웹이 전 경로에 토큰을 붙이는 일"(웹)을 **같은 웨이브**로 묶었다(설계 R1).

**신규 REST/RPC**: 신규 라우트·신규 RPC 메서드는 **없다**. 토큰은 전송 계층 관심사이므로 카탈로그에 메서드를 추가하지 않았다(기존 결정 유지).

**웹이 껍데기가 된 방식**: `web/token.js` 신설 — 토큰을 `localStorage['pa.viewerToken']` 에 보관하고, `mutFetch(url, init)` 하나가 모든 변이 요청에 `x-viewer-token` 헤더를 자동으로 붙인다. `web/app.js`·`web/roimaker.js` 의 변이 `fetch(` 35곳을 전부 `mutFetch(` 로 치환했다(치환 단위: 토큰 1개, `method:`/`body:` 는 손대지 않음). 웹에 남은 편집 로직은 "토큰 값을 어디서 읽어오는가"뿐이고, 언제 어떻게 보낼지는 서버 게이트가 결정한다.

### 2-2. W2 — 투어링(`capture.tour.*`)

**전제 반증(★ 착수 전 발견)**: 리더 지시문은 "서버에 이미 순회 로직이 있다"는 전제였으나, 조사 결과 `buildTouringPlan`(순회 순서 계산)은 **서버에 없고 `web/core.js:1689` 에만 있었다**. 따라서 이번 건은 "잡만 신설"이 아니라 **순회계획 순수함수 포팅 + 잡·라우트·RPC 신설 + 웹 껍데기화**까지 포함했다.

**웹에만 있던 것**: 순회 순서 계산(`buildTouringPlan`), 순회 루프·1초 대기·재진입 방지·진행 표시·완료 모달(`web/app.js:1876-1932 runTouringTest`).

**서버로 옮긴 것**:
- `src/setup/touringPlan.ts` — `web/core.js:1689` 를 자구 그대로 TS 로 포팅한 순수함수. 새 알고리즘 0줄.
- `src/capture/TourJob.ts` — 기존 `PlateDiscoveryJob` 과 같은 상태머신 패턴(`idle→running→(stopping)→done|aborted|error`)의 순회 잡. 카메라 이동·대기·정지만 소유하고 계획 산출은 위 순수함수에 위임. **DB·파일 쓰기 0**.
- `src/api/tourRoutes.ts` — 신규 라우트 3개(아래 표).
- `src/rpc/methods.ts` — `capture.tour.start`/`stop`/`status` 3개, 전부 `http` 위임(핸들러 로직 0줄).

### 2-3. W3 — 점유판정(`slot.occupancy.evaluate`)

**웹에만 있던 것**: 점유 판정 1단계(차량 접지밴드 argmax, `web/occupancy.js:152 OccupancyJudge.judge`)와 2단계(번호판 중심 폴백, `web/core.js:577 computeOccupancy`). 점유 **영역**(사다리꼴) 생성과 기하 프리미티브는 이미 서버에 있고 파리티로 봉인돼 있어 재작업하지 않았다.

**결정적 사실(★ 이 웨이브의 설계 핵심)**: 웹의 판정 함수(`updateLogicOccupancy`)는 **캔버스가 다시 그려질 때마다**(`drawRoiOverlay()` 안, 리드로 지점이 app.js 에 66곳) 호출됐다. 이걸 그대로 "함수 안을 fetch 로 바꾸는" 식으로 서버 왕복화하면 마우스 조작·캔버스 리사이즈·정밀수집 500ms 폴링마다 HTTP 가 나가 실사용이 불가능해진다. 그래서 껍데기화의 본체는 "호출 시점을 리드로에서 **데이터 변경점**으로 옮기는 것"이었다(§5 성능 참조).

**서버로 옮긴 것**:
- `src/domain/occupancyJudge.ts` — `web/occupancy.js`(1단계)+`web/core.js:computeOccupancy`(2단계) 자구 포팅. 기하 프리미티브(`geometry.quadCentroid`·`polygon.pointInPolygon` 등)와 상수(`GROUND_BAND_RATIO` 등)는 이미 서버에 봉인된 것을 **재사용**(값 복제 금지 — 리더 결정 Q2).
- `src/api/captureRoutes.ts` — `POST /capture/slots/judge-occupancy` 1라우트.
- `src/rpc/methods.ts` — `slot.occupancy.evaluate` 1개, `http` 위임.

**신규 REST 라우트**

| 메서드 | 경로 | 요청 본문 | 응답(200) |
|---|---|---|---|
| POST | `/capture/slots/judge-occupancy` | `{ frames: [{ key, floorPolygons:[{idx,quad}], detect?:{plates?,vehicles?} }], cfg?:{groundBandRatio?,minBandOverlap?}, regions?:boolean }` | `{ byKey: { [key]: { rows: OccupancyRow[], regions?: [{idx,scale,polygon}], overlapPairs?: [[n,n]] } } }` |

- **stateless**: cam/preset 을 받아 서버가 검출을 다시 돌리지 않는다(`POST /capture/detect` 는 카메라를 실제로 움직이므로 여기 끌어들이지 않았다). 카메라·DB·파일 **무접촉**, `mutating:false`.
- **오류코드**: zod 실패만 400(`-32602`). frames 빈 배열 → 200 `{byKey:{}}`. 퇴화 폴리곤 입력 → 200 + `occupied:false`(CONFLICT 로 올리지 않음 — 부작용이 없어 "사람 개입" 대상이 아니다). BUSY/CONFLICT/NOT_FOUND/UNAVAILABLE 은 이 라우트에서 **발생할 수 없다**(잡·카메라·파일·DB 를 아예 만지지 않는 stateless 판정이므로) — "해당 없음"이며 미구현이 아니다.

**웹이 껍데기가 된 방식**: `updateLogicOccupancy()`(동기 판정)를 `async refreshOccupancy()`(서버 배치 호출)로 교체하고, 호출 지점을 **데이터가 실제로 바뀌는 4곳**으로 좁혔다 — ①검출 도착(`runLiveDetect`) ①'검출 삭제(`deleteSelectedDetect`) ②ROI 로드(`loadPlaceRoi`) ③주차면 편집 커밋의 단일 funnel(`markPlaceDirty`, 추가·삭제·번호변경·전체삭제·되돌리기·정점이동 7곳이 전부 여길 거친다). `drawRoiOverlay()`·`renderSlotList()` 안에 있던 호출은 **삭제**했다. `web/core.js:buildFlatSlotRows` 시그니처를 `{placeRoi,detectByKey,parkingSlotsByKey,judge}` → `{placeRoi,parkingSlotsByKey,occByKey}` 로 바꿔, 내부 판정 분기를 **캐시 조회**로 대체했다. 적재 shape(`{id,occupied,source,center,vehicleRect,region}`)은 현행과 동일하게 맞춰 오버레이(원·사다리꼴)·슬롯목록 뱃지 소비 코드는 **무변경**이다.

### 2-4. W4 — 슬롯편집(`setup.slot.add` / `setup.slot.delete`)

**전제 반증(★ 착수 전 발견)**: 리더 지시문은 "슬롯편집이 `save/Setup_*.json` 과 DB 양쪽을 건드린다"는 전제였으나, 조사 결과 웹의 `addSlot`/`deleteSelectedSlot` 은 **메모리(`state.mapping`)만 고치고**, 영속화는 `PUT /mapping` → `data/setup_artifact.json` **단 하나**였다. 실제 위험은 "파일 충돌"이 아니라, `POST /mapping/renumber`(또는 `/mapping/placement`)가 artifact 를 **DB 로부터 통째로 재생성**해 추가한 슬롯이 사라지는 **순서 문제**였다(R10, 아래 §4 참조).

**웹에만 있던 것**: `nextSlotId`(결번 회피 slotId 생성)·`insertSlotAt`(명시적 splice 로 중간 삽입)·`removeSlot`(rebuild) — 전부 `web/core.js`.

- `src/rpc/methods.ts` — `setup.slot.add`·`setup.slot.delete` 2개, `http` 위임.

| 메서드 | 경로 | 요청 본문 | 응답(200) |
|---|---|---|---|
| POST | `/mapping/slot/add`(+`/viewer/api/mapping/slot/add`) | `{ camIdx, presetIdx, at?, rect?:{x,y,w,h}, zone?, artifact?, dryRun? }` | `{ ok:true, slotId, globalIdx, slots, globalCount, saved, warnings:[], dbSlotCount, artifact }` |

**웹이 껍데기가 된 방식**: `addSlot()`/`deleteSelectedSlot()` 을 `async` 화하고 편집 계산(`nextSlotId`·rect 리터럴·`insertSlotAt`/`removeSlot` 등)을 전부 제거, `mutFetch('/mapping/slot/add' 또는 '/delete', {artifact: <현재 버퍼>, dryRun:true, ...})` 로 대체했다. 웹은 `artifact`+`dryRun:true` 로 부르므로 **편집된 artifact 만 돌려받고 파일은 바뀌지 않는다** — 기존 "추가 → Ctrl+드래그 배치 → 저장" 2단계 UX 가 그대로 유지된다(아래 §3-② 참조). 남은 것은 `#map-msg` 가드·입력칸 읽기·`markDirty()`·3종 재렌더뿐, 편집 규칙은 웹에 0줄이다.

## 3. 핵심 설계 결정과 근거

### ① "RPC 는 로직을 갖지 않는다"

이번에 추가한 RPC 메서드 9개(`slot.occupancy.evaluate` 1 + `capture.tour.*` 3 + `setup.slot.*` 2 + W1 은 0개, 실제로는 tour3+occupancy1+slot2=6개가 카탈로그 수 증가분) 전부 `MethodDef.http`(REST 라우트로 위임하는 브리지 함수)만 갖고 있고, `handler`(RPC 자체에서 로직을 실행하는 경로)는 **하나도 쓰지 않았다**. 판정·계획 산출·편집은 전부 REST 핸들러(또는 그 아래 순수함수)가 소유한다. RPC 계층은 URL 조립과 파라미터 이름 매핑만 한다 — 그래서 "RPC 로 호출하든 REST 로 직접 호출하든 정본은 하나"라는 성질이 구조적으로 보장된다(W4 의 REST↔RPC md5 동일성 테스트가 이를 실측 확인했다).

### ② `dryRun` 으로 서버 정본화와 기존 2단계 UX 동시 만족(리더 결정 Q3)

슬롯편집은 서버 정본화하면 "즉시 반영"이 자연스럽지만, 기존 웹 UX 는 "추가 → 배치 → 저장" 2단계이고 추가 직후의 rect 는 화면 중앙 임시값이다. 즉시 반영하면 배치 전 임시 좌표가 파일에 남는다. 리더는 "라우트가 `dryRun` 을 지원하되 기본은 커밋"으로 결정했다 — 외부 RPC 호출자는 `dryRun` 생략(기본 `false`)으로 한 방에 커밋하고, 웹은 `artifact: <현재 버퍼>, dryRun:true` 로 호출해 계산 결과만 받는다. **두 경로 모두 같은 `artifactSlotEdit` 순수함수를 쓰므로 정본은 하나**이며, `dryRun:true` 는 `saveArtifact` 호출 자체에 도달하지 않아 파일을 절대 쓰지 않는다(md5 불변으로 봉인).

### ③ 파리티 기준변은 항상 `web/*`

3건(투어링·점유판정·슬롯편집)의 포팅 작업은 전부 "웹이 이미 실운영에서 검증된 쪽"이라는 원칙 아래, `web/*.js` 를 기준변으로 두고 서버 포팅본이 그것을 `toEqual` 깊은 비교로 따라가도록 설계했다. 입력은 새로 발명하지 않고 기존 테스트 케이스를 재사용했다(`test/occupancyJudge.test.ts` T1~T9, `test/slotInsertEdit.test.ts:16 sampleArtifact()` 등). 그래서 `web/core.js`·`web/occupancy.js` 의 포팅 대상 함수 4~6개는 **삭제하지 않고 그대로 남겨두었다** — 파리티 테스트와 기존 웹 전용 테스트(`test/buildTouringPlan.test.ts`·`test/occupancyJudge.test.ts`·`test/slotInsertEdit.test.ts`)의 기준변이기 때문이다.

### ④ DB 쓰기 0(DELETE+INSERT wipe 전례 회피)

2026-07-28 이전 라운드에서 `replaceSlotSetup`(DELETE+INSERT 방식 슬롯 재구성)이 검출·센터링 값을 통째로 날린 사고(memo 기록 "finalize slot_setup wipe fragility")가 있었다. 이번 4건은 설계 단계부터 **DB 쓰기 API 를 하나도 호출하지 않도록** 잡았다 — TourJob 은 store 를 주입받지도 않고, 점유판정 핸들러는 `deps` 자체를 받지 않으며, 슬롯편집은 `deps.sqlite` 를 `getSlotSetup()`(읽기)에만 쓴다. grep 으로 `replaceSlotSetup`/쓰기 API 호출 0건을 각 웨이브가 확인했다.

## 4. 작업 중 실제로 잡힌 결함

작업 도중 설계에 없던 실결함이 발견·수정됐다. W1~W4 자체 개발 과정에서 4건, 이후 독립 QA 검증과
리더 라이브 검증에서 추가로 3건(투어링 partial 상태 · D-1 슬롯편집 파일 전체 대체 · D-6 경고 문구 이어붙임)이
나와 총 **7건**이다. 은닉하지 않고 그대로 기록한다.

### 웹 `state.ptz` 부패 (W2 가 발견)

기존 웹 순회는 `move()` 로 카메라를 이동시켰고 `move()` 가 브라우저의 `state.ptz` 를 함께 갱신했다. 순회를 서버 잡으로 옮기면 **카메라는 실제로 움직이는데 브라우저의 기준 PTZ 값은 옛 값에 남는다** — 그 직후 방향/절대 이동을 누르면 "이전 위치로 되돌아갔다가 한 스텝만 움직이는" 증상이 생긴다(`test/viewerPtzSyncCoverage.test.ts` 머리말에 기록된 마스터 실측 증상과 같은 부류). 조치: `runTouringTest` 의 `finally` 에서 `await syncPtzAfterJob(null)` 을 호출하고, 그 라우트를 `viewerPtzSyncCoverage` 테스트의 `SYNC_OWNER['/capture/tour/start']='runTouringTest'` 로 등록해 이 호출이 앞으로 사라지면 테스트가 실패하도록 봉인했다. 이 인사이트는 설계서 §0-9 공통 규약(카메라를 움직이는 기능을 서버로 옮기면 PTZ 동기화 책임도 함께 옮긴다)으로 승격됐다.

### 미등록 라우트 2건 (T4 동적 검사가 발견)

`rpcParity.test.ts` 에 신설한 동적 등록검사(T4 — 완전 배선된 `buildServer` 인스턴스에 모든 RPC `http` 위임 URL 을 실제로 `app.inject` 해 Fastify 기본 404 가 아님을 단정)가 첫 실행에서 `capture.startPrecise → POST /capture/start-precise`, `capture.pipeline → GET /capture/pipeline` 2건을 검출했다. 두 라우트는 `deps.pipeline` 이 주입된 인스턴스에서만 등록되는데, 테스트 컨텍스트에 그 의존성이 없었다 — **정적 목록으로는 원리적으로 잡을 수 없는 종류의 결함**(카탈로그엔 있고 오타도 아닌데 실제로 등록되지 않은 상태)이다. `makeFullCtx` 에 `SetupPipeline` 을 주입해 해소했다.

### ★ R15 봉인 소실 — `mutFetch` 도입으로 PTZ 커버리지 정규식이 카메라 이동 라우트 8/9 을 놓쳐 green 인데 봉인은 없던 상태

W1 에서 웹의 변이 `fetch(` 를 전부 `mutFetch(` 로 치환했는데, `test/viewerPtzSyncCoverage.test.ts` 의 라우트 수집 정규식이 소문자 `fetch\(` 였다. 그 결과 **`mutFetch(` 로 나가는 요청은 이 테스트의 수집 대상에서 전부 빠졌다** — 실측: 수집 수 57 → 29 로 줄었고, 놓친 28개 중에는 카메라를 실제로 움직이는 라우트 9개 중 8개(`/capture/start`·`/capture/detect`·`/calibrate/ptz`·`/calibrate/point`·`/discover/ptz`·`/calibrate/lens/start`·`/capture/tour/start`·`/move`, GET 인 `/capture/pipeline` 만 생존)가 포함돼 있었다. 이 테스트의 첫 단정은 "수집된 것 중 미분류"를 보므로 **덜 수집할수록 통과가 쉬워져**, 테스트는 green 인데 봉인하려던 대상(카메라 이동 라우트)이 실제로는 하나도 검사되지 않는 상태가 됐다.

처음엔 "별건"으로 분류됐으나 설계자가 재판정해 심각도를 최상위로 올렸고("발견은 정확하나 심각도가 과소평가됐다"), W2 가 자기 웨이브 안에서 즉시 조치했다(대기가 순수 손실이라는 판단). 조치: 정규식을 `fetch\(` → `[Ff]etch\(` 1글자 수정 + 사유 주석 4줄 + tour 라우트 분류 3줄(diff 9 insertions / 1 deletion). 설계자가 W2 의 보고를 독립 재현해 수집 수(29→57)·미분류(0건)·diff 범위(9+/1-)·봉인 테스트(13 passed)·전체 회귀(2 failed 사전실패/3349 passed) 를 전부 일치 확인했다.

### 뷰어 컨텍스트 라우트 누락 시 웹 404 (W4 가 사전에 인지·대응)

웹의 `api()` 헬퍼는 실제로 `/viewer/api/*` 접두어가 붙은 경로를 호출한다. 슬롯편집 라우트를 헤드리스 경로(`/mapping/slot/*`)에만 등록했다면 웹 버튼은 그 접두어가 없어 **404 로 죽었을 것**이다. `renumber`/`placement` 라우트가 이미 헤드리스·뷰어 양쪽에 같은 클로저를 공유하는 선례가 있어, 슬롯편집도 동일 패턴으로 `/viewer/api/mapping/slot/add`·`/delete` 를 함께 등록했다. 테스트로 이 등록(웹이 부르는 바로 그 URL)을 고정했다.

### ★ 투어링 partial 결함 (리더 라이브 검증이 발견 → 즉시 수정)

리더가 워크트리 서버(포트 13021, 실카 Hucoms 192.168.0.153)를 띄워 28스텝(presets 5 + slots 23) 순회를
실측하는 중, "완주(`done 28/28`)인데 로그의 카메라 이동 명령이 1건뿐"이라는 관측이 나왔다. 조사 결과 원인은 둘이었다.

- **(착시 — 정상 동작)** `packetAggregator` 는 5분 창 안에서 **같은 키의 성공 패킷을 첫 1건만 기록하고 나머지는 집계**한다(실패는 항상 즉시 기록). 키가 `METHOD + 쿼리제거 URL + op` 라서 모든 `goptzfpos` 요청이 한 키로 묶인다 — 기존 `test/packetAggregator.test.ts` 가 이미 고정해 둔 동작이다. 5스텝으로 축소 재현해 스텝 수와 무관한 로그 정책임을 확인했다. **카메라는 실제로 매 스텝 이동했다.**
- **(진짜 결함)** 도달 불가능한 호스트로 붙여 재현하자, **28스텝이 전부 실패했는데도 `done 28/28 · skipped 0`** 으로 보고됐다. 실패를 흡수해 성공처럼 보여주는 상태였고, 이는 **헤드리스 검증(상태코드·완료 여부로 자동 판정) 목적 자체를 무력화**하는 결함이다.

**수정**: `TourStatus` 에 `succeeded`/`failed` 카운트를 항상 노출하고, `failed>0` 이면 종료 상태를 `done` 과
구분되는 **`partial`** 로 보고하도록 `TourJob`/`tourRoutes` 를 고쳤다. 웹은 이 경우 완료 모달 대신
`N개 위치 이동 실패(성공 M/T)` 문구를 표시한다. **`skipped`(계획 단계에서 애초에 제외된 수)의 의미는 그대로**다 —
`failed`(실행은 됐지만 실패)와 혼동하지 않도록 분리했다. 음성 대조로 수정 전 코드에서 실제로 4건 FAIL 함을 실증했다.

부수적으로 확인된 사실: 이 실카 환경의 `resolvePresetPtz` 는 항상 `null` 이다(`RealPtzSource.listCameras()`
가 PTZ 없이 카메라 1개만 반환하기 때문) — 그래서 프리셋 스텝은 전부 `requestImage` 이미지 폴백으로 처리됐다.
스텝당 관측된 ~703ms 지연의 주범은 `dwellMs` 대기가 아니라 `waitUntilSettled`(안정화 대기)였다.

이 결함은 §6 최종 검증 절 및 영향도 분석 문서 §6 후속 후보에도 반영돼 있다 — `partial` 상태 자체의
라이브 재현(실장비에서 204 를 받아 `failed:0` 만 나오는 경로)은 아직 미확인이다.

### ★ D-1(중) — `setup.slot.add`/`delete` 의 `artifact` 버퍼가 파일 전체를 대체하는 문제 (독립 QA 발견 → 수정)

독립 QA(`_workspace/03_qa_report.md` D-1)가 실제로 재현했다: 파일에 슬롯 2개(`c1p1s1`,`c1p1s2`)가 있는 상태에서
`POST /mapping/slot/add {camIdx:1, presetIdx:1, artifact:<c1p1s1 만 든 버퍼>}`(`dryRun` 미지정)를 호출하면,
기대는 3개(2+1)인데 실제로는 **2개** — 파일의 `c1p1s2` 가 조용히 사라졌다. `{...ARTIFACT, createdAt:'TAMPERED'}`
를 버퍼로 넣으면 디스크의 `createdAt` 도 그대로 `TAMPERED` 가 되는 것도 확인됐다.

**성격**: 리더 결정 Q3 의 설계(`artifact` 호출자 버퍼 + `dryRun`) 그대로 동작한 것이라 **코딩 버그는 아니다**.
문제는 "그 설계의 사정거리가 어디에도 적혀 있지 않았다"는 점이다 — 메서드 이름은 "슬롯 엔트리 1개 추가"이고
`warnings[]` 는 DB 개수 불일치만 알릴 뿐, "파일이 N슬롯 → 버퍼 M슬롯으로 통째로 대체됐다"는 사실은 침묵했다.
또한 설계서 R12("파괴 경로에 아예 진입하지 않는다")는 **DB 에 한해서만** 참이었고, 파일 쪽에는 열려 있었다 —
07-28 이전 라운드의 "검출·센터링 wipe" 사고와 **같은 계열**이 파일 쪽에 남아 있었던 것이다.

**수정**: `rejectBufferCommit()` 가드를 신설해, `artifact` 필드가 제공되고 `dryRun !== true` 인 요청을
zod 검증 직후·편집/저장 이전에 **409 / RPC `-32005 CONFLICT`** 로 차단한다. 허용되는 두 조합
(①`artifact`+`dryRun:true`=계산만, ②`artifact` 없이 커밋=디스크 정본 기준 편집)은 그대로 유지돼 **기능 손실이 없다**.
웹은 애초에 `artifact:<현재 버퍼>, dryRun:true` 로만 호출하므로 **웹 동작에는 영향이 없다**. 헤드리스·뷰어
컨텍스트 양쪽 테스트로 확인했고, 음성 대조로 가드 제거 시 5건 FAIL 함을 실증했다(`mappingSlotRoutes.test.ts` 계열).

### D-6(경미) — `addSlot` 경고 문구가 직전 문구에 이어붙던 문제 (독립 QA 발견 → 수정)

직전에 남아 있던 문구 뒤에 이어붙이는 방식(`msg.textContent = `${msg.textContent} — ...``)이었다 — 반복 호출할

## 5. 음성 대조 규약(설계서 §9.2) — "green 이 곧 봉인 작동은 아니다"

이번 작업 전체에 걸쳐, 새 봉인(파리티 테스트·정적 커버리지 테스트)을 추가할 때마다 **그 봉인이 실제로 잡아내는 변이를 한 번 보여주고 원복**하는 절차를 실천했다(W2 가 R15 처리에서 이 방식을 처음 세웠고, W3·W4 가 계승했다). 예:

- W3 `occupancyJudgeParity`: `quad.length !== 4` → `< 4` 로 완화한 변이가 FAIL 1건 검출. `bandArea <= 0` → `< 0` 완화도 FAIL 1건 검출. 반면 tie-break `>` → `>=` 변이와 `pointInQuad` 의 `length<3` 가드 제거는 **검출되지 않았다** — 이유까지 확인해 "웹·서버가 동일 식이라 애초에 갈릴 수 없는 지점"임을 정직하게 기록했다.
- W4 `artifactSlotEditParity`/`mappingSlotRoutes`: 결번 회피 로직 제거(A), clamp 완화(B), md5 무조건 저장(D), 409 가드 무력화(E), `NO_MOVE` 표 삭제(F) — 5건 전부 FAIL 로 검출. `removeSlot` 의 `rebuildGlobalIndex` 인자를 필터 안 된 옛 presets 로 바꾼 변이(C)만 검출되지 않았는데, 이는 "의미상 등가 변이"(반환값이 실제로 같다)임을 확인해 정직하게 기록했다.

이 규약의 취지는 "봉인 테스트가 통과한다"는 사실 자체가 아니라, **그 봉인이 무너진 코드에서 실제로 떨어지는지**를 한 번은 증명하는 것이다.

### ★ 독립 QA 가 이 규약을 더 넓게 적용해 발견한 판별력 구멍 6건 → 영구 편입

독립 QA(`_workspace/03_qa_report.md`)가 3종 파리티(`touringPlanParity`·`artifactSlotEditParity`·`occupancyJudgeParity`)에
**변이 17건**을 직접 주입해 재측정한 결과 **10 검출 / 7 미검출**이었다. 미검출 7건 중 6건은 "픽스처가 그 갈림을
만들 수 없는 입력만 갖고 있어서" 생긴 **진짜 봉인 구멍**이었고(예: `groundBandRatio 오버라이드`라는 이름의 기존
테스트 3개가 실제로는 폴리곤이 rect 의 y 범위를 전부 덮어 **ratio 에 둔감한 기하**라 오버라이드가 무시돼도
통과했다 — 이름이 거짓말하는 테스트), 1건(`bestRatio >= minBandOverlap` → `>` tie-break)만 "web·server 가
동일 식이라 원리적으로 갈릴 수 없는" 의미상 등가 변이였다.

리더 지시로 이 6건을 **임시 프로브로 버리지 않고 영구 케이스로 편입**했다(기존 케이스는 무수정, 추가만):
`touringPlanParity` +2 · `artifactSlotEditParity` +2 · `occupancyJudgeParity` +3(`groundBandRatio` 는 "민감도
자체 확인" 가드 1개 + 파리티 1개로 2개 소비). 영구 파일 위에서 6건의 변이를 **재주입해 전부 FAIL** 함을 실증했고,
실패한 it 이름이 전부 신규 케이스임을 확인해 "기존 케이스가 우연히 같이 잡은 것이 아님"을 증명했다. 결과
**파리티 3종의 최종 판별력은 17건 중 16 검출 / 1 원리적 불가**로 올라갔다.
