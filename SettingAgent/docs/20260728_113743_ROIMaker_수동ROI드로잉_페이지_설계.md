## 0. 한 줄 요약

선택된 카메라·프리셋 화면 위에 마우스로 주차면 폴리곤을 직접 그리고(좌클릭 정점 추가 → 우클릭 폐합), 기존 ROI 는
정점 드래그로 수정하며, 저장 시 **정본 `PtzCamRoi.json` 과 DB `slot_setup.slot_roi` 를 함께 갱신**하는 전용 페이지를
SPA 새 탭으로 추가한다. **핵심 설계 목표는 "저장이 기존 검출·점유·센터링 데이터를 파괴하지 않는 것"** 이다.

### 1.1 마스터 확정 사항 (2026-07-28 추가 지시)

| # | 지시 | 확정 사양 |
|---|---|---|
| 13 | 삭제는 **선택된 주차면 슬롯의 "순수 그려진 ROI만"** 삭제 | **슬롯 엔트리·전역 idx 는 남기고 폴리곤(points)만 비운다.** → idx 집합 불변 → **재압축 없음 → DB 아이덴티티 재매핑 없음**(§8 위험 2 원천 소멸). 아직 저장 전인 신규 space 는 버퍼에서 완전 제거 |
| 14 | 선택·기존 슬롯 ROI **출력 유지** + 보기 콤보 3종 | `#rm-view-scope`: `현재 프리셋만`(기본) / `현재 슬롯만` / `전체 보기`. 목록·캔버스 **양쪽**에 적용. 선택했다고 나머지가 사라지지 않는다 |
| 15 | N≠4 강등 **수용**. "수동 ROI 는 현재 페이지에서만 보게" | 미저장 편집 버퍼는 **ROIMaker 페이지 로컬**(제어탭·정밀수집에 새지 않는다). 저장 후에는 정본 파일이 바뀌므로 다른 페이지에도 반영되는 것이 정상(요구 12) |
| 16 | **순간 스냅샷 사용 가능** | §3 D-6 프레임 고정 채택 확정 |

**#13 의 파급 (설계가 크게 단순해진 지점)** — 삭제가 "행 제거"가 아니라 "기하 비우기"이므로:
- `PtzCamRoi.json` 의 `parking_spaces[].idx` 집합이 항상 1..N 순열로 유지된다 → `normalizeGlobalIdx` 영구 무변경.
- DB 는 `slot_setup` 행을 지우지 않고 `slot_roi='[]'` 로 UPDATE 한다 → **검출·점유·센터링 컬럼 보존**.
- `sync-roi` 의 매칭 키 `(cam_id, preset_id, preset_slotidx)` 가 삭제에도 흔들리지 않는다.

**빈 폴리곤(`points: []`) 의 다운스트림 안전성** — 구현 1단계에서 실측 확인할 항목(§9.2 케이스 9):
`pointInQuad`(`length<3` → false), `hitTestQuadVertex`(`length<3` → null) 은 안전. `polygonCentroid([])` ·
`groundInputs` · `occupancyRegion` 의 빈 배열 처리는 **테스트로 확인 후 필요 시 가드 추가**한다.

### 범위에서 **제외**한 것 (근거 있는 제외)

- **슬롯 엔트리 자체의 삭제**(주차면 행 제거): 마스터 지시 #13 에 따라 ROIMaker 는 기하만 비운다. 행 제거는
  기존 제어탭 `주차면 목록·편집` 패널(`index.html:157` `#place-delete`)이 담당한다(중복 금지).
- 폴리곤 전체 이동(내부 드래그), 정점 추가·삭제(중간 삽입), Undo 스택: 요구에 없음 → 넣지 않는다(규칙 2 단순함 우선).

## 3. 설계 결정 (트레이드오프 공개)

### D-1. 페이지 형태 — SPA 새 탭 + 전용 뷰 (선택) vs 독립 HTML

| 안 | 장점 | 단점 |
|---|---|---|
| (가) **SPA 새 탭 + 전용 뷰·전용 JS** ✅ | 소스/카메라/프리셋 선택·라이브 스트림·PTZ·인증 기계를 그대로 씀. 신규 미검증 면적 최소 | `index.html`/`app.js` 에 탭 1개 배선 필요 |
| (나) 독립 `roimaker.html` | 완전 격리 | 소스·카메라·프리셋 드롭다운, 스트림 시작/재시도 백오프, 배지, 로그인까지 **전부 복제** → 메모 기록상 최대 리스크인 "브라우저 미검증 면적"이 급증 |

**(가) 채택.** 단 "새 페이지"의 취지(전용 화면·간섭 없음)는 **전용 뷰포트 + 전용 캔버스 + 전용 JS 모듈**로 만족시킨다.
`setTab('roimaker')` 은 analyze/options/db 와 같이 기존 `.viewport-wrap`/`panel` 을 숨기고 `#roimaker-view` 만 띄운다.

### D-2. 저장 시 DB 반영 방식 — **차등 동기**(선택) vs 기존 전량 재적재

| 안 | 결과 |
|---|---|
| (가) 기존 `POST /capture/slots/load-roi` 재사용 | `loadRoiIntoDb` → `replaceSlotSetup` = **DELETE + INSERT 전량**. `vpd_bbox`·`lpd_obb`·`occupy_range`·`pan/tilt/zoom`·`centered`·`img1`·`slot3d_front_center` **전량 소실**. 메모 `finalize slot_setup wipe fragility` 가 기록한 그 파괴 |
| (나) **신규 `POST /capture/slots/sync-roi` (차등·비파괴)** ✅ | `slot_roi` 만 UPDATE / 신규만 INSERT / 파일에 없는 행은 **삭제하지 않고 보고**. 검출·점유·센터링 보존 |

**(나) 채택.** 근거: ROI 손보정은 **반복적·일상적** 조작이다. 한 번 그릴 때마다 센터라이징 결과가 날아가면 워크플로가
성립하지 않는다. (가)는 "전체 재적재" 버튼(`#cap-load-roi`)으로 이미 존재하므로 그 경로는 그대로 두고 건드리지 않는다.

`sync-roi` 는 **본문 없이(`{}`) 호출**한다. 서버가 방금 저장된 정본 파일을 다시 읽어 `buildSlots()` 로 기대 행을
만들고 현재 `slot_setup` 과 비교한다 — **클라이언트가 DB 조작을 지시하지 않는다**(정본은 파일 하나).

**매칭 키 = `(cam_id, preset_id, preset_slotidx)`.** 삭제를 범위에서 뺐고 신규는 항상 배열 끝에 append 하므로
이 키는 편집 세션 동안 안정적이다(§8 위험 2 에 이 전제의 붕괴 조건을 명시).

**차등 규칙**

| 상태 | 동작 |
|---|---|
| 파일·DB 양쪽 존재, `slot_roi` 상이 | `slot_roi` + `updated_at` 만 UPDATE. 타 컬럼 무접촉 |
| 파일·DB 양쪽 존재, `slot_id` 불일치 | **중단**(0건 반영) + `error` 반환. 아이덴티티가 어긋난 상태에서 쓰기 금지 |
| 파일에만 존재 | INSERT(enrichment 컬럼 전부 NULL, `centered=0`) |
| DB 에만 존재 | **삭제하지 않음** + `orphans[]` 로 보고. 자동 파괴 금지 |
| 파일 파싱 실패 / 유효 주차면 0 | 무변경 + `ok:false`(`loadRoiIntoDb` 의 안전 규약과 동일) |

### D-3. 정본 파일 저장 범위 — 변경 프리셋만 (선택)

`PUT /capture/place-roi` 는 `applyPlaceRoiUpdate`(`placeRoi.ts:120`)로 **대상 프리셋의 `parking_spaces` 를 통째 교체**한다.
→ 클라이언트는 **그 프리셋의 전체 space 목록**을 보내야 한다(일부만 보내면 나머지 소실).

ROIMaker 는 **현재 편집 중인 프리셋 1개만** PUT 한다. 기존 `savePlaceRoi()`(`app.js:1935`)의 "전 프리셋 순차 PUT" 은
쓰지 않는다 — 손대지 않은 프리셋까지 재작성하면 §8 위험 1(정규화 탈락 소실)의 노출면이 불필요하게 넓어진다.

### D-4. 저장 전 무결성 가드 — `expectRawCount` 옵션 (선택)

메모 2026-07-28 기록: `idx` 없는 주차면이 `normalizePtzCamRoi` 에서 조용히 탈락 → `applyPlaceRoiUpdate` 통째 교체로
**8면 → 7면 소실**. 이 결함은 **현재도 `PUT /capture/place-roi` 경로에 살아 있다**.

ROIMaker 는 정본을 직접 덮어쓰는 도구이므로 이 가드는 speculative 가 아니라 **실사고 대응**이다.

- `PUT /capture/place-roi` 본문에 **옵셔널** `expectRawCount:number` 추가.
- 제공 시: 쓰기 직전 원본 raw `parking_spaces.length` 와 비교 → 다르면 **409 + 무변경**.
- 미제공 시: **현행 동작 그대로**(기존 호출자 = 자동보정 저장 무영향).

### D-5. 그리기/편집 모드 분리 (요구 8~11)

```
정지(idle)  ──[시작 버튼]──▶  그리기(drawing)
   ▲                              │
   └──────[정지 버튼 / 폐합]──────┘
```

- **정지**: 정점 드래그 편집(요구 7) + 목록 선택. 좌클릭 = 정점/폴리곤 선택.
- **그리기**: 좌클릭 = 정점 추가, 우클릭 = 폐합, `Esc` = 진행 중 폴리곤 취소, `Backspace` = 마지막 정점 취소.
  폐합하면 **자동으로 정지로 복귀하지 않고** 그리기 모드를 유지한다(연속 드로잉 — 주차면은 보통 여러 개를 연달아 그린다).
- 두 모드는 **좌클릭 의미가 배타적**이라 한 화면에서 동시 지원이 불가능하다. 이것이 요구 11("토글 없어도 됨")을
  따르지 않은 유일한 이유다.

### D-6. 그리기 중 배경 프레임 — 시작 시 **고정(freeze)** (선택)

- 정지 상태: `<img id="rm-frame">` 에 라이브 MJPEG(기존 `/viewer/api/stream` 재사용).
- **시작 누르는 순간** 현재 프레임을 `drawImage` 로 오프스크린 캔버스에 복사해 배경으로 고정하고 스트림을 정지한다.
- 근거: 흔들리는 영상 위에서는 정점을 맞출 수 없다. 그리고 **그리는 도중 PTZ 가 움직이면 좌표계 자체가 달라져**
  이미 찍은 점이 무의미해진다. 고정은 정확도와 정합성을 동시에 얻는다. 서버 신규 엔드포인트 불필요(클라이언트만).
- 정지로 돌아가면 라이브 재개.

### D-7. 좌표 규약

- 화면 이벤트 → 정규화: `(e.clientX - rect.left)/rect.width` (기존 `eventToNorm`, `app.js:1220` 동일 식).
- 메모리·DB·전송 = **정규화 0~1**(원점 좌상단). 정본 파일 = **픽셀**(`applyPlaceRoiUpdate` 가 `imageWidth/Height` 로 역변환).
- 영속화 수치는 **소수점 5자리**(`stringify5`) — 메모 `SettingAgent persist 5 decimals` 규약.

### D-8. 저장 후 UI 갱신 — 서버 재조회 (선택)

낙관적 갱신(로컬 상태를 그대로 화면에 반영)은 하지 않는다. 저장 성공 후 `GET /capture/place-roi` + `GET /capture/slots`
를 다시 읽어 렌더한다. 근거: 정본은 서버 파일이고, 정규화·전역번호 재부여가 서버 쪽에서 일어날 수 있다.

## 5. 데이터 모델

```js
// roimakerCore.js 상태(순수 — DOM/전역 미참조)
{
  mode: 'idle' | 'drawing',
  draft: { points: [{x,y}, ...] } | null,   // 진행 중 폴리곤(정규화)
  spaces: { "cam:preset": [{ idx, points:[{x,y}...] }] },  // 편집 버퍼(= placeRoi 형태 동일)
  selected: { key, idx } | null,
  dirtyKeys: Set<"cam:preset">,             // 저장 대상 프리셋
}
```

- **버퍼 우선 규약**: 그리기·드래그는 전부 메모리 버퍼만 바꾼다. 파일·DB 는 **저장 버튼에서만** 변한다
  (기존 `place-save` 규약과 동일 — 사용자가 되돌릴 수 있다).
- **삭제(지시 #13)** — 두 갈래:
  - `origin:'file'`(파일에 이미 있는 space): `points: []` 로 **비우기만** 한다. `idx`·배열 위치 유지 →
    파일 idx 집합 불변, DB 는 `slot_roi='[]'` UPDATE(행·타 컬럼 보존).
  - `origin:'new'`(이번 세션에 그린 미저장 space): 버퍼에서 **완전 제거**(파일·DB 에 아직 없으므로 안전).
- **신규 space 의 `idx`(전역 slot_id)** = `현재 파일 전체 space 수 + 1`(=N+1). 배열 끝에 append.
  근거: `normalizeGlobalIdx` 는 **idx 집합이 1..N 순열이기만 하면 무변경**(`placeRoi.ts:103`)이므로,
  어느 프리셋에 붙든 N+1 을 주면 기존 slot_id 가 하나도 바뀌지 않는다 → DB 는 INSERT 1행으로 끝난다.

## 8. 위험 · 함정

1. **[상] 정본 소실 — `normalizePtzCamRoi` 조용한 탈락.**
   `idx` 없는 raw space 는 정규화에서 탈락하고 `applyPlaceRoiUpdate` 가 통째 교체하므로 파일에서 사라진다.
   메모에 실사고(8→7면) 기록. → **D-4 `expectRawCount` 가드로 차단.** 단 **근본 수정은 아니다**
   (탈락분을 보존하지는 못한다 — 사용자가 `idx` 를 채워야 한다). 기존 `PUT` 경로의 결함은 그대로 남는다.

2. **[상→해소] 전역 idx 재압축 = DB 아이덴티티 재매핑.**
   삭제로 idx 에 gap 이 생기면 `normalizeGlobalIdx` 가 다음 로드에서 1..N 을 **재부여**하고, DB `slot_id` 와
   조용히 어긋난다. → **마스터 지시 #13(ROI 만 비우고 슬롯 엔트리는 유지)으로 이 위험이 원천 소멸**한다(§1.1).
   ⚠ **잔존 붕괴 조건**: 제어탭의 기존 `#place-delete`(행 제거)를 쓴 뒤 ROIMaker 로 오면 idx 가 재부여돼 있을 수 있다.
   → 진입 시 `normalizeGlobalIdx` 의 `changed` 를 확인해 **재부여 시 저장 전 경고**, 그리고 `sync-roi` 의
   `slot_id` 불일치 중단 규칙(§3 D-2)이 2차 방어선으로 작동한다.

3. **[상] DB 전량 wipe.** `replaceSlotSetup` 은 DELETE+INSERT 다. ROIMaker 는 **절대 이 경로를 타지 않는다**
   (§3 D-2). 기존 `#cap-load-roi`(전체 재적재) 버튼은 무변경으로 남긴다.

4. **[중] N≠4 폴리곤의 기능 열화(요구 3 의 실제 대가).** 조사 결과 **크래시는 없고 전부 graceful 강등**이다:

   | 기능 | 위치 | N≠4 동작 |
   |---|---|---|
   | 지면모델 추정 표본 | `ground/groundInputs.ts:35` | 그 면 **제외** |
   | 육면체 축 표본 | `ground/contact.ts:197` | 그 면 **제외** |
   | 슬롯 3D 앞면중심 | `ground/slotFrontCenter.ts:15` | `null` |
   | 지면 역투영 | `ground/project.ts:141` | `null` |
   | 점유영역(occupy_range) | `domain/occupancyRegion.ts:75` | `null` |
   | 육면체 표시 | `web/core.js:1556` | `null`(미표시) |
   | 주차면 배정 | `capture/spaceAssign.ts` | **안전**(`pointInPolygon`/`polygonCentroid` 사용) |
   | 점유 판정 | `web/core.js:765 pointInQuad` | **안전**(N각형 지원) |

   → **5점 이상은 "그릴 수 있고 저장되고 표시되지만, 그 슬롯은 지면모델·육면체·점유영역에서 빠진다."**
   이 사실을 UI 배지와 저장 응답 issues 로 **정직하게 노출**한다. 조용히 틀리게 만들지 않는다.

5. **[중] 브라우저 실렌더 미검증 — 7라운드 누적.** 이 저장소에 DOM 자동화가 없어 `web/*` 변경은 육안 검증이
   불가능하다(메모 반복 기록). ROIMaker 는 신규 `web/` 코드가 **~600줄**로 이번 변경의 최대 미검증 면적이다.
   → 완화: ① 순수 로직을 `roimakerCore.js` 로 최대한 밀어내 vitest 로 덮는다 ② DOM id·배선·호출 순서를
   **정적 봉인 테스트**로 고정(`cameraKindSelect.test.ts` 선례) ③ **마스터 육안 확인이 완료 기준에 포함**된다.

6. **[중] 정적 자산 캐시.** `web/*` 는 nodemon 감시 밖이고, **기존 탭은 하드리로드(Ctrl+Shift+R) 전까지 옛 JS**로 돈다
   (메모 2026-07-24 함정). 검증 시 반드시 하드리로드 선행.

7. **[하] 라이브 스트림 이중 점유.** 제어탭과 ROI 탭이 동시에 MJPEG 를 열면 카메라 부하가 2배다.
   → `setTab` 진입/이탈에서 **한쪽만 스트림을 유지**하도록 명시적으로 stop/start.

8. **[하] `viewerPtzSyncCoverage` 등록 누락.** 신규 라우트를 분류에 등록하지 않으면 **기존 테스트가 실패한다**
   (메모 2026-07-27 기록). 구현 체크리스트에 포함.
