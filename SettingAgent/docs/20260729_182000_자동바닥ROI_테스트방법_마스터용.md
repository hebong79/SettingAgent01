## 1. 눈으로 보기 — 오버레이 PNG (가장 직관적)

이미 생성돼 있다. IDE 에서 열기만 하면 된다.

```
SettingAgent/reports/overlay_r15/v1/overlay_1_1.png     ← 골든 v1
SettingAgent/reports/overlay_r15/v2/overlay_1_1.png     ← 골든 v2
```

프리셋 5개 전부 있다: `overlay_1_1` · `overlay_1_2` · `overlay_1_3` · `overlay_2_1` · `overlay_2_2`.

### 색 읽는 법
| 색 | 의미 |
|---|---|
| **초록 실선** | **수동 정본 = 정답** (사람이 그린 주차면) |
| **빨강 점선** | **자동 검출 결과** — 이게 초록에 붙을수록 좋다 |
| 노랑 굵은 선 | 알고리즘이 고른 **전방선**(주차면 앞쪽 경계) |
| 파랑 | 고른 분리선(주차면 사이 경계) |
| 주황 ○ | 근변 코너 |
| 회색 흐린 선 | 검출된 전체 직선(후보들) |

좌상단 검은 박스에 `f`(초점거리)·`camH`(자가보정된 카메라 높이)·검출 면수가 찍힌다.

### ★ 이렇게 보면 이번 라운드 핵심이 보인다
**v1 과 v2 의 같은 파일명을 나란히 열어라.** 같은 PTZ·같은 코드인데 프레임만 다른 두 결과다.
특히 `overlay_1_2.png` 의 `camH` 를 비교하면 **4.98m(v1) → 5.22m(v2)**, 같은 장면인데 추정 높이가 4.8% 움직인다.

### 직접 다시 뽑기
```bash
cd SettingAgent
npx tsx src/tools/roiAutoOverlay.ts test/fixtures/roiAutoGolden    reports/overlay_r15/v1 data/Place01/PtzCamRoi.json 0
npx tsx src/tools/roiAutoOverlay.ts test/fixtures/roiAutoGolden_v2 reports/overlay_r15/v2 data/Place01/PtzCamRoi.json 0
```
마지막 인자 `0` = 디더 시점 인덱스(0~5). `0` 이 기저 시점이다.

## 2. 수치로 확인 — 라이브 채점

### 2-A. 빠른 확인 (단일 시점, **12초**)

```bash
curl -s -X POST http://localhost:13020/rpc -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"roi.auto.score","params":{"camId":1,"presetIdx":1,"consensus":false}}'
```

읽기 좋게(파이썬 있으면):
```bash
curl -s -X POST http://localhost:13020/rpc -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"roi.auto.score","params":{"camId":1,"presetIdx":1,"consensus":false}}' \
| python -c "import sys,json;r=json.load(sys.stdin)['result']['presets'][0];print('mean',round(r['meanIoU'],5),'frame',r['detect']['frameHash']);print([round(s['iouVsManual'],4) for s in r['slots']])"
```

**볼 것**: `meanIoU`(1.0 이 완벽) · `slots[].iouVsManual`(면별 점수) · `detect.frameHash`(어느 프레임이었나).

**프리셋 바꾸기**: `camId` 1 또는 2, `presetIdx` 1~3.
현재 대상 = `1:1`(7면) · `1:2`(4면) · `1:3`(2면) · `2:1`(6면) · `2:2`(4면).

## 7. ★ 테스트하면 보게 될 현상 — 미리 알아둘 것

**같은 명령을 두 번 돌리면 결과가 크게 다를 수 있다.** 이건 버그 재현이 아니라 **이 프로젝트가 지금 싸우고 있는 현상 그 자체**다.

2026-07-29 18:0x 실측, `1:1` 다시점 합의 채점 연속 2회:

| | 평균 IoU | ≥0.95 | 자가보정 지상고 | 근변선 재적합 |
|---|---|---|---|---|
| 1회차 | **0.97474** | **7/7** | 5.000 → **4.956m** (계수 0.99122, 표본 23) | **pass1·pass2 실행** |
| 2회차 | **0.85541** | **0/7** | 5.000 → **5.051m** (계수 1.01025, 표본 21) | **실행 안 됨** |

읽는 법:
- 참 설치고는 **4.950m** 이다(F6, 3중 독립 확인). 1회차는 그쪽으로 맞게 갔고(4.956), **2회차는 정반대로 갔다**(5.051).
- 자가보정이 **방향을 뒤집는 이유**는 관측 칸간격이 2.5221m vs 2.4746m 로 **1.9% 달라졌기 때문**이고, 그건 프레임 화소가 미세하게 달라서다.
- 그리고 **높이가 틀린 쪽에서는 근변선 재적합이 아예 안 돈다** — 좋은 결과를 만드는 보정 단계가 통째로 빠진다.

반면 **단일 시점**(`consensus:false`)은 3회 연속 전부 **0.97474 · 7/7** 로 안정적이었다(프레임은 매번 달랐다).

> **결론**: 지금 성적을 흔드는 것은 "운"이 아니라 **지상고 자가보정이 프레임 미세차를 증폭해 방향을 뒤집는 것**이고, 그 뒤집힘이 재적합 단계를 죽인다. 16회차가 치려는 표적이 정확히 이것이다.

### 그래서 테스트할 때
- **1회만 돌린 수치로 판단하지 마라.** 최소 2~3회 돌려 편차를 보라.
- 수치를 기록할 땐 **반드시 `frameHash` 를 같이 적어라.** 해시 없는 IoU 는 해석할 수 없다(F13).
