## 0. 왜 만들었나 — 솔직하게

마스터 실카 화면 신고: **"점 4개를 찍은 후 사각형이 그려지지 않는다."**

이 결함은 **7라운드 연속 미검증이던 브라우저 렌더 영역**에서 처음 드러난 실결함이다. 지금까지 리더·설계자·구현자·검증자 전원이 브라우저에 접근할 수 없어 "코드가 그 자리에 있다"까지만 증명해 온 영역을, 마스터의 실사용이 뚫었다.

### ★ 리더 진단이 틀렸고 설계자가 정정한 것

리더는 최초 진단에서 원인을 **`drawPlaceDrawOverlay`(app.js) 의 `closePath()` 누락**으로 단정했다. 그러나 설계자가 코드 근거로 반박했고, 검증자가 독립 재현으로 확정했다:

- `placeDrawClick`(4점째 클릭 처리)에서 **4점째는 렌더를 거치지 않고 같은 동기 블록에서 즉시 커밋**되고, `endPlaceDraw()` 가 `state.placeDraw = null` 로 만든다.
- 따라서 `drawPlaceDrawOverlay` 가 `pts.length === 4` 상태로 호출되는 **경로가 애초에 존재하지 않는다**(mousemove 도 `if (!state.placeDraw) return`).
- **`closePath()` 만 추가하면 화면은 1픽셀도 바뀌지 않는다.**

**실제 원인**은 두 가지였다.
1. 3점 단계까지는 **닫힘 예고가 없어** 사용자가 "이게 사각형이 될지" 알 수 없었다.
2. 4점째 커밋 후 보여야 할 **초록 파일 ROI 가 `#roi-floor` 토글 게이트에 막혀 화면에 나타나지 않았다.**

**이는 직전 라운드의 미리보기 무반응 결함과 완전히 같은 유형이다** — 동작은 성공했는데 화면 변화가 0이라 사용자는 실패로 인식한다. `ggPreview` 는 `#roi-auto` 를 강제로 켜주는 선례가 있는데, 그리기 커밋 경로에는 그 대응이 빠져 있었다. **같은 실수를 두 번 한 것**이며, 이번 라운드가 그 구멍을 메운다.

## 1. 무엇을 만들었나

### 1-1. 렌더 결함 수정

- `drawPlaceDrawOverlay` — 3점째에 **p3→p1 점선 닫힘 예고**(`setLineDash([4,4])`)를 추가해, 4점째를 찍기 전에 "이게 곧 사각형이 됨"을 시각으로 알린다. `closePath()`/채움은 리더 지시대로 **방어 코드로만** 추가했고(4점 분기는 실행 도달 불가), 그 사실을 소스 주석에 명시했다.
- `ensureFloorVisible()` 신규 헬퍼 — `#roi-floor` 토글을 강제 ON 한다(사용자 명시 조작 직후에만 호출, `ggPreview`의 `#roi-auto` 강제 ON 선례와 같은 규약). **4개 진입점**에 배선했다:
  1. 그리기 시작(`togglePlaceDraw`)
  2. 4점 커밋(`placeDrawClick`)
  3. 정점편집 ON(`place-edit-vertex` change)
  4. 목록 행 선택(`selectPlaceSpace`) — QA 결함 F-3 대응으로 추가
  전부 **렌더(`drawRoiOverlay`) 호출보다 먼저** 배치해 "토글은 켜졌는데 그 프레임엔 안 보이는" 1프레임 지연을 없앴다.
- 정점 핸들의 `#roi-floor` 의존은 **그대로 둔다**(표시 조건과 히트테스트 조건이 이미 대칭이라, 한쪽만 떼면 "안 보이는 사각형을 드래그"하는 더 나쁜 상태가 생긴다). 대신 위 4개 진입점에서 토글을 강제로 켜 무반응을 없앴다.

### 1-2. ROI 초기화(`#place-clear`)

```
그리는 중이면      → 찍은 점 전부 삭제. 그리기 모드는 유지("1/4" 로 재시작).
아니고 면 선택 중이면 → 그 면 삭제(deletePlaceSpace() 위임 — 신규 삭제 로직 0).
아니면            → "지울 점도, 선택된 주차면도 없습니다" 안내, 무동작.
```

우선순위는 **그리는 중 > 선택 면**(비파괴 분기를 항상 앞에 둔다). 파일 접촉은 없다(메모리 `state.placeRoi`까지만, 저장은 별도 '저장' 버튼에서만 발생).

### 1-3. 전체삭제(`#place-clear-preset`)

- 범위: **`currentFrameKey()`**(화면에 보이는 cam:preset) — `drawFileFloorRoi` 가 그리는 대상과 동일 기준이라 "보이는 것을 지운다"는 사용자 기대와 일치.
- `confirm()` 로 파괴 전 확인. 확인문에 범위·미저장 상태·되돌리기 가능 여부·전역번호 재부여 사실을 전부 명시.
- idx 정합: `clearPresetSpaces(placeRoi, key)` **신규 순수함수**(`web/placeDraw.js`) — 대상 프리셋의 idx 를 **큰 것부터** 골라 기존 `core.js` `removePlaceSpace` 를 접어서 전량 위임한다. **`core.js` 는 수정하지 않았다.** "전체삭제 = 기존 '삭제' 버튼을 n회 누른 것"과 동일한 위험 등급이라는 것이 설계 근거이며, 검증자가 대조 실험으로 "큰 idx부터"가 장식이 아니라 정확성 조건임을 확인했다(작은 idx부터 접으면 대상 키가 안 비워짐).

### 1-4. 되돌리기(`#place-undo`)

- `snapshotPlaceRoi(label)` / `sealPlaceRoiUndo()` 헬퍼로 **초기화·전체삭제가 같은 1단계 스냅샷**(`state.placeRoiUndo`, 전체 맵 깊은 복사)을 공유한다. QA 가 지적한 F-1(초기화의 면 삭제가 스냅샷 없이 복구 불가)을 이 라운드에서 되돌리기 일원화로 해소했다.
- 자동보정 전용 `state.placeRoiBackup` 과는 **완전히 분리**(교차 참조 0, 버튼도 `#place-undo`/`#align-undo` 별개).
- `sealPlaceRoiUndo` 가 파괴 직후 결과를 `JSON.stringify` 지문으로 봉인하고, `undoPlaceRoi` 는 그 지문이 **다를 때만**(=실제로 그 사이에 다른 편집이 있었을 때만) 추가 확인을 묻는다(QA F-2 대응). 매번 뜨는 경고는 읽히지 않는다는 판단.
- 스냅샷은 **1단계만**(다중 undo 스택 없음). `savePlaceRoi` 성공 시 소진.
- `confirm` 은 **의도적으로 미부착**(초기화의 면 삭제 분기): 이제 되돌리기로 복구되므로 F-1 의 핵심(무확인·무복구)이 사라졌고, 같은 일을 하는 기존 `삭제` 버튼이 확인을 받지 않아 동작을 갈리게 하면 오히려 혼란이 커진다고 판단했다.

### 1-5. UI 배치

`.roi-edit-bar` 를 **2행**으로 분리했다(기존 id·클래스·CSS 무변경). 1행 = 그리기(비파괴), 2행 = 목록/파일(파괴 있음, 좌→우 파괴 강도 오름차순: 삭제 → 전체삭제 → 되돌리기 → 저장).

## 2. 입출력 · 계약

- 서버(`src/**`)는 **완전 무변경**이다. 초기화·전체삭제·되돌리기는 전부 클라이언트 메모리(`state.placeRoi`) 조작이며, 파일 반영은 기존 '저장' 버튼(`savePlaceRoi` → `PUT /capture/place-roi`)에서만 일어난다. 이 계약은 세 함수 본문에 `fetch` 가 0줄임을 검증자가 확인했다.
- `PUT /capture/place-roi` 자체의 REST 계약은 변경되지 않았다. 전체삭제가 만드는 "빈 배열 저장"은 **기존 스키마가 이미 허용**하는 입력이다(`PlaceRoiPutSchema.spaces` 는 `min` 없는 `z.array`) — 이번 라운드가 새 서버 동작을 만든 것이 아니라 기존 계약의 경계값을 처음 실사용하는 것뿐이다.
- 신규 함수 시그니처:
  ```js

  export function clearPresetSpaces(placeRoi, key);

  // web/app.js (DOM/state)
  function ensureFloorVisible();
  ```

### 3-2. 본체 성립 — 코드 전수 확인 (검증자)
- `drawFileFloorRoi` 의 실질 게이트는 **1개**(`#roi-floor` 체크). 두 번째 조건(`FLOOR_ROI_USE_LLM`)은 상수 `false`라 사실상 죽은 조건.
- 게이트 통과 이후 **초록 면을 막는 조건은 0개**이고, 호출 위치도 `roiHidden||!mapping` 가드보다 앞이라 수집 중·artifact 없음에도 그려진다.
- `ensureFloorVisible` 호출 4곳 전부가 `drawRoiOverlay()` 호출보다 **먼저** 실행됨을 소스 인덱스 비교로 확인.

### 3-3. 독립 재현 — 3점 닫힘 예고 (검증자)
배포 소스 원문(`drawPlaceDrawOverlay`) 60줄을 그대로 실행하고 baseline과 대조:
- 1점·2점·2점+커서 시퀀스가 **변경 전과 완전 동일**(회귀 0).
- 3점에서 실제로 `save → setLineDash([4,4]) → beginPath → moveTo(p3) → lineTo(p1) → stroke → restore` 발행 확인 — p3(300,100)→p1(100,100)로 정확히 닫힘.
- 4점 분기(closePath+fill)는 명령 자체는 발행되지만, **그 분기로 실행이 도달하는 경로는 없음**을 코드 흐름 추적으로 재확인(도달 불가 확정).

### 3-4. idx 정합 — 랜덤 500케이스 (검증자)
- `clearPresetSpaces` 결과 전부 **1..N 순열 유지**, `normalizeGlobalIdx(...).changed === false`, 원본 미변형.
- "큰 idx부터 접는다"가 장식이 아니라 **정확성 조건**임을 대조 실험으로 실증(오름차순으로 접으면 대상 키가 `1:2=[4]`처럼 잔존해 깨짐).
- 서버 왕복(빈 배열 PUT → 재로딩)도 직접 실행으로 확인: `applied===true`, 재로딩 후 `byPreset keys=['1:2'] idx=[1]`.

### 3-5. F-1 수정 실행 증명 (구현자, 배포 소스 원문 5함수 절단 실행)
```
[1] 1:1=[idx1,idx2] 1:2=[idx3] 선택=2
→ [2] 초기화 클릭 → 1:1=[idx1] 1:2=[idx2] 선택=null 스냅샷=있음
→ [3] 되돌리기 → 1:1=[idx1,idx2] 1:2=[idx3]
복구 성공(좌표까지 바이트 동일) = true / 1..N 순열 유지 = true
```
`1:2` 의 면이 idx 3→2로 재압축됐다가 되돌리기로 3으로 정확히 복원 — 프리셋 단위 undo였다면 불가능했을 지점이다(전체 맵 스냅샷 선택의 실증).

## 5. ★ 한계·미검증 (위장 금지 — 전부 기록)

- **브라우저 실렌더는 여전히 미확인이다.** 진입점 4/4가 됐고 게이트가 1개뿐임을 코드로 확인했지만, "토글이 켜지면 실제로 초록 면이 화면에 뜬다"는 **코드 경로 확인까지**다. 실제 픽셀은 아무도 보지 못했다. **마스터 육안 확인이 1순위.** `confirm()` 실제 모달, 3점 점선의 시인성(색·굵기·대비), 2행 레이아웃 줄바꿈, 실서버 HTTP 왕복(PUT→파일쓰기→GET 재로딩) 전부 브라우저/서버 없이는 검증 불가능해 미확인 상태다.
- **`place-delete`(기존 삭제 버튼)로 지운 면은 여전히 복구되지 않는다.** 리더 요구는 "초기화·전체삭제 양쪽"이었고, `place-delete` 자체를 손대는 것은 범위 밖으로 뒀다.
- **F-2 지문의 오탐률은 전수 확인하지 않았다.** `JSON.stringify` 는 키 순서에 의존하며, 확인한 편집 경로(`assemblePlaceRoi`·spread)는 순서를 보존하지만 모든 경로를 다 보진 못했다. 오탐 시 결과는 "확인창이 한 번 더 뜬다"뿐이라 데이터 위험은 없다고 판단했다.
- QA 의 F-4·F-5는 [정보] 등급이고 리더 수정 지시에도 없어 미조치 — 다음 라운드 판단 사항.
- **별건(이번 범위 아님)**: 마스터 실카 캡처의 자동ROI 격자 셀이 주차면 1대보다 훨씬 커 보인다(`auto cam1 p01 8/10`). 실카 격자 스케일 의심 — 그리기 정상화 확인 뒤 별도 확인 필요.
- 이월: R2(단일 quad `focalFromVPs` f²≤0) 근본 미해결 · `normalizePtzCamRoi` 조용한 탈락 잔존 · `allowNew` UI 미노출 · Unity 튜닝값 미조정.

## 6. 원칙 고지

"코드 경로 확인"과 "화면에서 봤음"은 이 문서 전체에서 **엄격히 구분**했다. 육안 미확인 항목을 완료로 적지 않았고, 실행 주체(리더/구현자/검증자)가 다른 수치는 그대로 인용했다.
