## 2. 왜 이렇게 했나 — 리더 결정 D-1/D-2/D-3

### D-1. 정본 = 파일(PtzCamRoi.json) 갱신. DB 직접 쓰기 0줄.

`slot_setup.slot_roi` 를 쓰는 코드는 저장소 전체에 정확히 2곳(`Finalizer.persistSlotSetupFromPlace`, `roiDbLoad.buildSlots`)뿐이고, **둘 다 소스가 PtzCamRoi.json** 이다. LLM 폴리곤 경로(`resolveFloorPolygon`)는 반환값을 `void` 로 버리고 런타임에 배선돼 있지 않아 `slot_roi` 와 무관하다(설계 단계에서 "LLM vs 자동격자 충돌"로 예상했던 것은 실재하지 않았고, 진짜 충돌은 "파일 ROI vs 자동 격자"였다).

결정적 이유: `Finalizer.persistSlotSetupFromPlace` 는 매 finalize 마다 `replaceSlotSetup`(DELETE+INSERT 전량 교체)을 PtzCamRoi.json 소스로 호출한다. **자동 격자를 DB 에만 쓰면 다음 finalize 에서 반드시·조용히 소멸한다.** 따라서 자동 격자는 승인 시 기존 `PUT /capture/place-roi` 와 동일한 경로(`applyPlaceRoiUpdate`)로 **PtzCamRoi.json 을 갱신**하고, DB 반영은 기존 finalize/load-roi 가 그대로 담당하도록 했다. 결과: 신규 DB 쓰기 코드 0줄, `replaceSlotSetup` 호출자 증가 0 — Requirements 의 "replaceSlotSetup 취약성 가드"가 이 구조로 원천 회피된다.

### D-2. 신규 수학은 "프리셋 불변 지면 2D 좌표계" 1건뿐.

`GroundModel` 의 `n,d` 는 프리셋별 카메라 좌표계 값이라, 격자를 카메라 좌표에 두면 프리셋을 건널 수 없다("1면 → 전 프리셋"이 원리적으로 불가능해진다). 다리는 기존 `slotBearingDeg`(방위 불변량)의 역으로 구성했다 — 원점=카메라 나딜(세계 고정점), 축=pan 보정 기저. 이 40~90줄이 `groundFrame.ts` 이고, 나머지는 전부 `groundModel.ts`/`project.ts` 의 기존 함수(`estimateGroundVPs`, `focalFromVPs`, `buildGroundPlane`, `poolFovBaseV`, `focalFromZoom`, `slotBearingDeg`, `projectToPixel`)를 재사용했다. 그 결과 `groundModel.ts`·`project.ts`·`types.ts`·`floorRoi.ts`·`Finalizer.ts`·`SqliteStore.ts`·`roiDbLoad.ts`·`web/core.js` 8파일은 **변경 0줄**이며, 이는 구현자 주장에 그치지 않고 검증자가 `git diff --numstat` 로 독립 재확인했다(§5).

### D-3. Loop 3 성공기준을 "홀드아웃 대조"로 교체.

리더가 원래 제시한 기준(`crossPresetSimilarityChecks` 통과: `dDevRel<10%`, `bearingDevDeg<8°`)은 **자동 모델에 대해 항진명제(tautology)** 다 — 자동 모델은 `d` 를 같은 상수에서 복사하고 방위도 같은 격자에서 나오므로 이 값들은 정의상 0이 되어 아무것도 검증하지 못한다. 설계자가 이를 지적했고 리더가 승인한 대안은: preset1 quad 1개로만 부트스트랩 → preset2·3 의 auto 모델을 **같은 preset 의 파일 quad 로 독립 추정한 모델**과 대조(`|Δd|/d<10%`, `|Δtilt|<1.0°`, `|Δf|/f<5%`, 기존 임계 재사용, 신규 검증기 0개). 부수 규약으로 자동 모델의 `metricErr=0`/`tiltErr=0` 은 "품질이 아니라 구성상 0"이므로 `conf` 를 1.0으로 채우지 않고 부트스트랩 프리셋의 conf 를 상속하며, `AUTO_MODEL_ISSUE` 정직성 문구를 issues 에 항상 부착한다.

## 3. ★ 최종 명제 — 정확한 범위 (과장 금지)

### ✅ 성립: "주차면 1개 → **그 프리셋 · 그 주차열**의 전 슬롯"

실데이터(`data/Place01/PtzCamRoi.json`, Unity 시뮬레이터 생성분) 기준 QA 수정 라운드 최종 실측:

| cam | preset | 파일 슬롯 | 결과 |
|---|---|---|---|
| 1 | 1 | 7 | matched 7/7, avgIoU **0.99998** |
| 1 | 2 | 4 | matched 4/4, avgIoU **1.00000** |
| 1 | 3 | 2 | matched 2/2, avgIoU **1.00000**(§4-3 fovBaseV 폴백으로 부트스트랩 성공) |
| 2 | 1 | 6 | matched 6/6, avgIoU **0.99999**(자동 `colStart` 탐색으로 성공) |
| 2 | 2 | 4 | matched 4/4, avgIoU **1.00000** |

→ **5/5 성공, 평균 IoU 0.99998~1.00000.** QA 검증 라운드에서는 4/5(cam1 preset3 부트스트랩 실패)였으나, 구현자의 fovBaseV 폴백 수정으로 5/5 로 개선됐다(§4-3).

### ❌ 불가: "주차면 1개 → 카메라의 **모든 주차열**"

이 데이터셋은 카메라당 **주차열이 3개(cam1) / 2개(cam2)**이고, **정보 한계**로 인해 한 열의 드로잉으로 다른 열을 알아낼 수 없다. 증명 3종(구현자·검증자 독립 재확인):

1. **medResid 불변량(닫힌 형태)**: `medResid` 는 최근접 격자점까지의 거리이며 창(colStart/rowStart)을 어디로 옮겨도 격자점 집합 자체는 불변이므로 변하지 않는다. cam1 preset1→preset2 의 `medResid=1.321m` 은 임계 0.25m 의 5.3배이고, 격자 평행이동은 2.5m 정수배만 가능하므로 어떤 이동으로도 0으로 만들 수 없다.
2. **1만 셀 확장(실행)**: 창을 200×50=10,000칸까지 넓혀도 preset2/preset3 의 matched 는 0에서 변하지 않았다(자기 열 preset1 만 matched=7 유지).
3. **533회 전수 스윕(실행)**: `colStart -20..20 × rowStart -6..6` 전수 조합에서도 preset2 의 최대 matched 는 0.

정량적 근거: preset1↔preset2 행 간격 = 15.59m = rowPitch(5.0m)의 **3.118배(정수배 아님, 주차통로)**. 열 위상차 = **1.318m(슬롯폭 2.5m의 0.527배)**. cam2 도 preset1(theta=0°)/preset2(theta=90°)로 동일하게 서로 다른 열이다(검증자가 독립 재측정으로 확인 — 오히려 구현자 보고보다 과소 보고였음을 지적).

원리 논증: 입력(quad 1개+PTZ)에서 결정되는 것은 ①지면 평면(n,d) ②카메라 상수 ③**그 셀 1개**의 위치·방위뿐이다. 다른 열의 위상·방위는 입력의 어떤 함수로도 표현되지 않는 자유 파라미터다. 이는 구현 한계·모델링 한계가 아니라 **정보 한계**다.

### ⚠️ 미증명(반증 아님): "주차면 1개 → 그 열의 **전 프리셋**"

아키텍처는 교차 프리셋 이식을 지원하고, 투영도 실제로 그 프레임에 닿는다(cam1 preset2 프레임 안에 preset1 슬롯 #4·5·6 이 실제로 투영되어 들어온다는 것을 확인했다). **하지만 실데이터에서 적용까지 성사된 사례는 0건이다** — preset2 의 파일 슬롯(8,9,10,11)은 preset1 이 그린 열과 **다른 열**이라 IoU 매칭이 안 되고(`unmatchedFile=[8,9,10,11]`), `applicable=false` 로 거부된다. 이는 "이식 불가"의 반증이 아니라, **이 파일이 각 열의 슬롯을 한 프리셋에만 배정해서 이식할 대상 자체가 없기 때문**이다. 판정에 필요한 데이터(한 열이 두 프리셋에 걸쳐 등록된 사례)가 이 저장소에 없다 — "확인 필요"로 남긴다.

### ★ 구현자가 스스로 발견해 수정한 결함(QA·구현자 모두 이전 라운드에서 놓쳤던 것)

우선순위 1(결함 5)을 측정하는 과정에서 격자를 넓게 펼치자(cols=60, rows=20), **90° 뒤집힌 다른 주차열**의 슬롯과 우연히 `IoU 0.3995`/`0.3769` 로 매칭되어 `applicable=true` 가 되는 사례가 드러났다. `fileCount=matched` 조건만으로는 이를 걸러낼 수 없어, **적용됐다면 정상 ROI 를 40%만 겹치는 엉뚱한 quad 로 조용히 덮어썼을 것**이다 — 리더 원칙("조용히 틀린 ROI 보다 안 그리는 게 낫다") 정면 위반 사례였다.

**2중 방어선으로 수정**:
1. (주된 방어) **on-lattice 슬롯만 매칭 후보**로 제한 — off-lattice(다른 주차열)는 IoU 가 우연히 높아도 후보에서 제외한다. IoU 운에 의존하지 않는 기하학적 게이트.
2. (보조 방어) `MATCH_MIN_IOU` **0.3 → 0.5** 상향(같은 슬롯이면 실측 IoU 가 0.99 이상 나오므로 0.5 는 충분한 여유).

수정 후 동일 조건 재현: `preset3: matched=0, applicable=false, offLattice=[12,13]` — 적용되지 않는다. 부수적으로 `PresetPlan` 에 `onLattice`/`offLattice`/`medianResidM` 진단 필드를 추가해, `matched=0` 의 원인이 "창 문제(자동 선택이 해결)"인지 "다른 주차열(창을 옮겨도 불가)"인지 사용자가 구분할 수 있게 했다.

## 6. 한계·미검증 (위장 금지)

1. **브라우저 실렌더/sharp 픽셀 대조 — 미확인.** `web/app.js` 변경은 (a) 문법 체크 (b) 정적 봉인 테스트 (c) 라우트 응답 계약까지만 확인했다. 특히 QA 수정 라운드에서 `web/app.js` 를 표 컬럼 2개 추가로 **또 건드려**, 미검증 면적이 오히려 **늘었다**. `#roi-auto` off 상태의 픽셀 동일성은 `git diff --numstat web/app.js`(187 insertions/0 deletions, 기존 줄 무변경) + `drawAutoRoi` 첫 줄의 early-return 이라는 **정적 논증**으로만 뒷받침되며, 스샷 대조는 CLAUDE.md 규칙 3(동작 확인)의 미완 항목으로 남는다.
2. **`allowNew` 가 UI 에 미노출.** 라우트에는 `allowNew: z.boolean().default(false)` 가 있으나 `web/app.js` 에는 0건. 즉 **웹 경로는 현재 기존 슬롯 좌표 교체만 가능**하고, 신규 주차장(파일에 space 가 0개인 프리셋)에서 슬롯을 늘리려면 라우트를 직접 호출해야 한다. QA 는 "지금 상태(UI 미노출)가 더 안전하다"고 권고했고, 구현자는 `rows>1` + `allowNew` 조합이 주차통로 위에 가짜 슬롯을 써넣을 위험(B-3) 때문에 **의도적으로 남겨 두었다**.
3. **`ON_LATTICE_MAX_M=0.25`, `MATCH_MIN_IOU=0.5` 는 Unity 데이터로 튜닝된 값**이다. 실카에서 재조정이 필요할 수 있다 — 너무 빡세면 정상 슬롯을 거부(안전 실패), 너무 느슨하면 §4 의 오매칭 결함이 재발한다.
4. **모든 IoU 1.0000 류 수치는 Unity 생성 픽스처 기준**이다. PTZ 가 정확하고 격자가 구조적으로 완벽하다. 파이프라인 수학이 무손실이라는 것만 증명하며, 실카메라에 대해서는 아무것도 말하지 않는다.
5. **불규칙 배치(사선주차)는 범위 밖**이다. 격자 파라미터로 표현할 수 없으므로 수동 드로잉을 유지한다.
6. **cam1 preset3 는 단독으로는 f 를 낼 수 없다**(`focalFromVPs` f²≤0). 같은 카메라의 다른 프리셋에서 `fovBaseV` 를 빌려 해소했으나, **다른 프리셋에 주차면이 하나도 없는 카메라는 여전히 불가**하고 수동 드로잉으로 대체해야 한다.
7. **`upsertCameraGrids` 의 격자 이력**: QA 수정 라운드에서 `gridKeyOf`(열 동일성 키) 기반으로 "같은 열=갱신, 다른 열=추가"로 개선했지만, 이 갱신 로직 자체의 실카 대응 실측은 없다.
