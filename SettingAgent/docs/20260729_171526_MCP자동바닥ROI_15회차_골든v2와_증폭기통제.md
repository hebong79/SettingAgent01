## 1. 라운드 성격

측정 라운드다. 이번 라운드에 점수(≥0.95 통과면수)를 올리려는 알고리즘 변경은 0줄이다. 목표는 **실카 이행 준비물 2종**을 만드는 것이었다 — ① 정착 프레임 평가 프로토콜(골든 세트 v2), ② 자가보정 증폭기 통제(지상고 정책 A/A0/B/C 비교). 14회차가 "같은 PTZ·같은 코드에서도 잡힌 프레임에 따라 통과면수가 ±6면 흔들린다"는 측정 타당성 붕괴를 확인했고, 그 대응으로 15~16회차를 "시뮬 점수 트랙 종료 → 실카 이행 준비물 공장"으로 전환한 것이 이번 라운드의 배경이다.

## 2. ★ 이번 라운드 최대 성과 — 재적합 교락 발견 (설계자)

설계자가 `bayGrid.ts:508`을 추적해 발견한 사실:

```ts
const calib = probe ? calibrationFromGrid(probe.evidWidths, probe.result.phaseM, model, opts) : null;
if (!calib) return { best, tried, issues };   // ← 여기서 반환하면 ③ 재적합 루프(523~556)에 도달하지 못한다
```

`if (!calib) return ...`이 ③ 근변선 2자유도 재적합 블록(523~556) **앞**에 있다. 따라서 `calibrateHeight:false`는 지상고 자가보정만 끄는 것이 아니라 **근변선 재적합도 동시에 끈다.**

→ **14회차가 인용한 `CALIB=0` 수치(1:1 0.85541→0.93182, 2:1 격차 0.115→0.0002)는 "지상고 보정을 껐더니 좋아졌다"가 아니라 "보정+재적합을 껐더니 좋아졌다"로 정정해야 한다.** 이 교락 때문에 리더는 A0(보정 ON + 재적합 OFF) 통제군 추가를 승인했다.

**A0 실측 수확**(v1 기준, 21면 중 ③ 변형 ≥0.95 통과면수): **A 13면 → A0 8면** — **근변선 재적합이 단독으로 5면을 만들고 있다.**

## 3. ★ QA가 반증한 것 — 구현자 1차 결론이 틀렸다 (은닉 금지)

### 3-1. 구현자 1차 결론

> "B 모드는 v1↔v2 평균이 5자리까지 동일(G2=0.00000) = 프레임 무관. B는 2/2 프리셋에서 정확히 0.00000 — 프레임이 바뀌어도 IoU가 한 자리도 움직이지 않는다."

### 3-2. QA 적대적 검증 결과 — **반증**

- **0.00000은 `toFixed(5)` 반올림 산물이다.** 8자리 프로브 결과 `1:1` B③ 평균이 v1 **0.95579193** / v2 **0.95579226**로, 실제 격차는 **3.3×10⁻⁷**다. 면별로도 6자리에서 갈린다(s1 +2×10⁻⁶, s5·s6·s7 −1×10⁻⁶).
- **"완전히 다른 6장"이 아니다.** v1↔v2 프레임을 화소 단위로 대조하니 `1:1` d0의 화소 차이는 **3.298%**, 8레벨(255 기준) 초과 차이는 **703개(0.034%)**, **평균절대차(MAD) 0.0554/255**였다. 두 세트는 사실상 같은 장면이다.
- **같은 로그 안에서 이미 반증되는 대목이 있었다.** 변형 ④(융합)에서는 `1:1` B가 v1 0.95908 / v2 0.95905로 5자리에서도 움직인다(Δ=3×10⁻⁵). "B는 IoU가 한 자리도 움직이지 않는다"는 서술은 구현자 자신의 로그로도 성립하지 않았다.
- **결정적 실험**: v2의 `1:1` d0 자리에 v1 d3 프레임(같은 프리셋의 다른 디더 = 진짜로 다른 장면)을 주입 → **0.95579 → 0.25387**로 붕괴. 채택 근변선 `c`가 −723.35→−766.99, quads 7→6으로 갈렸다. **B는 프레임 의존이다.**
- 자가보정 경로의 증폭도 직접 관측했다 — `1:1` d0의 자가보정 지상고가 **4.956123 → 5.051264(+1.92%)**로 튄다(A 경로).

### 3-3. 살아남는 문장 / 죽는 문장

| 구분 | 문장 |
|---|---|
| **죽는 문장** | "자가보정을 끄면(B) IoU가 프레임에 완전히 무관해진다(격차 0.00000)" |
| **살아남는 문장(권고 정정문)** | "동일 섭동(화소 MAD 0.055, 유의차 화소 0.03%)에 대해 A는 IoU 0.11933, A0는 0.09192, C는 0.09119가 움직이는 반면 B는 3.3×10⁻⁷만 움직인다 — **감도 비 약 3.6×10⁵**. 단 B도 프레임 의존이며, 프레임이 실제로 바뀌면(다른 디더 프레임 주입) 0.956→0.254로 무너진다." |

## 7. C 모드 2:2 = 0.00000 붕괴의 원인 (QA 확정 — 버그 아님)

구현자가 세운 버그 가설 3건을 QA가 전부 실측으로 기각했다: null/NaN 없음(6시점 자가보정 전부 유효), `medianLow` 입력 길이 6 정상, 공유 지상고 5.032747m(공칭 대비 +0.65%, 게이트 15% 안) 정상, 6시점 전부 quads=4 생성.

**진짜 원인은 득표 동점 해소다.** `2:2`는 기저 시점 d0이 원래부터 틀린 행에 latch 해 있다. A는 군집이 `{1,3,5}`(3표) / `{0,4}` / `{2}`로 갈려 대표가 **d1**이라 0.94182가 나오지만, C는 고정 지상고(5.0327m)가 각 시점 latch 행을 바꿔 군집을 `{0,4}` / `{1,5}` / `{2}` / `{3}`로 파편화시켜 **2:2 동점**이 되고, `roiAutoFuse.ts:337`의 "동점 시 최소 인덱스 우선" 규칙이 틀린 행에 있는 d0을 대표로 뽑아 0이 된다.

**구현자 추정("고정 지상고 탓")은 정정된다.** B도 고정 지상고인데(4.950m) 군집이 A와 완전히 동일해(`{1,3,5}` 대표 d1) 0.93630이 나온다. 무너뜨린 것은 "고정 지상고"라는 방식 자체가 아니라 **C가 고른 특정 값 5.0327m**이다. `2:2`는 지상고를 4.950→5.033(+1.7%)으로 올리면 시점별 latch 행이 갈리는 **임계 프리셋**이며, 이 취약성은 C 고유도 아니다(A도 `2:2` 미보정 분기에서 대표가 d0이라 ②=0.00000).

- **F16**(QA 정정본 채택): 자가보정 ON 경로는 MAD 0.055 수준의 미세 프레임 차이를 IoU 0.09~0.12로 증폭한다. OFF 경로(B)의 감도는 3.3×10⁻⁷다 — **이것은 "무관성"이 아니라 "저감도"이며, 프레임이 실제로 크게 바뀌면(다른 디더 프레임 주입) B도 0.956→0.254로 붕괴한다.**

구현자가 최초로 제안한 F16 초안("자가보정을 끄면 IoU가 프레임에 완전히 무관해진다")은 QA 반증(§3)에 따라 폐기하고 위 정정본으로 교체한다.

## 12. 실카 이행 선행물 보고 (P3 — 실행 0건)

아래 5개 항목은 **모두 실행하지 않았다.** 마스터 결정·운영 작업이 필요한 항목만 근거·결정 주체·예상 작업량과 함께 정리한다.

### ① 실카 PTZ 프리셋 정의

- **현황**: 실카에는 `"현재 위치"` 1개 프리셋만 있다(14회차 §18-⑥ 정찰 확인). 시뮬처럼 프리셋별로 지면모델(pan/tilt/zoom/설치고)을 주입하는 구조는 이 입력이 없으면 그대로 돌지 않는다.
- **필요 결정 주체**: 운영(현장) — 어느 주차 행을 몇 개 프리셋으로 볼 것인지는 현장 배치를 봐야 정할 수 있다. 카메라 확정(③)과 순서가 얽혀 있다.
- **예상 작업량**: 운영 결정 자체는 현장 답사·PTZ 프리셋 등록(하드웨어 조작) 수준. 이후 SettingAgent 쪽 반영은 config/정본 소규모 추가(구현 라운드 1회 이내로 추정).

### ② 실카 채점용 수동 정본 작성 절차

- **현황**: R1(수동 정본은 채점 전용, 검출·기하·선택 입력 금지)을 실카에서도 지켜야 한다. 정답지 없이는 goal/loop 성공기준이 수렴 판정을 할 수 없다 — 이것이 없으면 실카 라운드를 시작해도 "좋아 보인다"는 관찰형 판단으로 흐르게 된다(14회차 이전에 이미 배제한 방식).
- **필요 결정 주체**: 마스터(수동 정본 작성 주체·절차 확정) — 시뮬 정본과 같은 스키마로 작성할지, 실카 전용 도구가 필요한지 결정 필요.
- **예상 작업량**: 프리셋 수 × 슬롯 수만큼의 수동 좌표 입력(현재 시뮬은 21면). 실카 프리셋 수가 확정돼야(①에 종속) 정확한 물량이 나온다. 도구화가 필요하면 구현 라운드 1회 추가.

### ③ 카메라 확정

- **현황**: `real-camera-1`은 `focalTrue` 표본을 92/112개 보유해 자체 캘리브레이션이 있다. `real-camera-2`는 자체 캘리브 없음(`model: cam-001`). U15 확정 사실 — 펌웨어 f 값을 그대로 믿으면 최대 **7.7%** 오차(zoom 3000: 실측 2403.53 vs 펌웨어 2588.87)가 난다.
- **권고**: `real-camera-1` 채택.
- **필요 결정 주체**: 마스터.
- **예상 작업량**: 결정 후 `config/tools.config.json`의 `selectedCameraId` 1줄 변경 + 재정찰 확인(수 분). 단 §13(영향도)에서 다루는 config 되돌림 이슈와 얽혀 있어 실카 재개 시점에 함께 처리 필요.

### ④ paintMask 백색 차량 오염 대응 — 설계 방향 스케치만 (구현 금지)

- **근거**: 실카 정찰(14회차 §18-②) 결과 백색 픽셀 6.79%(시뮬 1.99~5.67%), 관측된 20대 이상 차량 중 절반 가까이가 백색·은색이었다. 시뮬은 차량이 어두워 백색≈도색선이었으나, 실카에서는 `paintMask`가 차체로 오염될 가능성이 높다.
- **스케치 수준의 방향**: 도색선은 얇고 긴 직선 구조인 반면 차체 반사는 국소 덩어리(blob) 형태라는 점을 이용한 라인 구조 필터(세장비·연속성 기준) 등. **이번 라운드에서 코드로 구현하지 않았고, 구현 여부·구체 설계는 16~17회차 실카 이행 시 별도 설계 라운드가 필요하다.**
- **필요 결정 주체**: 마스터(실카 이행 착수 승인 후 설계자).
- **예상 작업량**: 설계 1라운드 + 구현/검증 1~2라운드로 추정(정찰 데이터가 정량 측정이 아니라 확정치는 아님).

### ⑤ 시뮬 씬 흰 차량 배치 가능 여부

- **질의 사항**: 시뮬 씬에 흰색 차량을 배치할 수 있다면, ④의 오염 리허설을 실카 없이 시뮬에서 먼저 돌려볼 수 있다.
- **필요 결정 주체**: 마스터/엔진(씬) 담당 — 현재 미확인.
- **예상 작업량**: 가능 여부 확인은 질의 1회. 가능하다면 씬 편집 작업량은 별도 산정 필요(이번 라운드에서 산정하지 않음).
