### 2-2. MCP — 파일 수정 0, 메서드 자동 증가

`GET /rpc/catalog` 메서드 수가 70 → 76 으로 늘었다(§구현 문서 §6). MCP 의 `setting_rpc_catalog`/`setting_rpc` 도구(`src/mcp/server.ts`)는 이 카탈로그를 **그대로 프록시**하므로, 이번 4건 작업에서 **MCP 파일은 한 줄도 수정하지 않았음**에도 MCP 를 통해 호출 가능한 메서드가 자동으로 6개 늘었다(tour 3 + occupancy 1 + slot 2). 이는 설계 의도대로다 — RPC 카탈로그가 단일 출처이기 때문이다. **76 이라는 수는 독립 QA(`app.inject` 로 `count=76` 실측)와 리더 라이브 검증(포트 13021 에서 `GET /rpc/catalog` 실호출) 양쪽에서 재확인됐다.**

MCP 프로세스가 여전히 `cfg.viewer.controlToken` 을 읽어 `x-viewer-token` 을 자동 주입하는 동작(`src/mcp/server.ts:34`)도 이번 작업으로 바뀌지 않았다. 단, 아래 §3 의 "같은 config" 주의사항이 그대로 적용된다.

### 2-3. 뷰어(웹) — 실제로 호출하는 URL 이 늘었다

웹은 `/viewer/api/*` 접두어로 호출한다. 슬롯편집 2라우트는 헤드리스 경로뿐 아니라 **뷰어 컨텍스트 경로**(`/viewer/api/mapping/slot/add`·`/delete`)에도 등록됐다(같은 클로저 공유) — 이 등록이 없으면 웹 버튼이 404 로 죽는다는 것을 구현 중 실제로 인지하고 대응했다(§구현 문서 §4).

## 3. 운영 주의

### 3-1. `viewer.controlToken` 활성화 순서 — 웹 토큰 배선이 먼저 배포돼야 한다

`viewer.controlToken` 을 빈 문자열에서 실제 값으로 바꾸는 순간, `controlGate` 훅이 등록되어 **모든 변이 요청**(면제목록 제외)에 토큰이 필요해진다. W1 에서 웹의 변이 요청 35곳 전부를 `mutFetch` 로 옮겨 토큰을 자동 부착하도록 했지만, 만약 이 웹 배선(app.js/roimaker.js) 이 배포되지 않은 상태에서 서버 설정만 먼저 켜지면 **웹 버튼 다수가 403 으로 죽는다**(원래 31곳이 미배선이었던 지점). 서버 게이트와 웹 배선은 **같은 배포 단위**로 나가야 한다.

### 3-2. MCP 프로세스와 서버가 같은 config 를 읽어야 한다

MCP 는 `cfg.viewer.controlToken` 값을 그대로 읽어 요청에 자동으로 실어 보낸다. **MCP 프로세스가 읽는 config 파일과 실제 서버가 구동 중인 config 파일이 다른 값**(예: 하나는 빈 문자열, 하나는 실제 토큰)을 가리키면 MCP 를 경유하는 모든 변이 요청이 **전부 403** 으로 실패한다. 배포·운영 시 두 프로세스가 동일 config 경로를 참조하는지 반드시 확인해야 한다.

### 3-3. ★ config 상태 — 라이브 검증에 실제로 사용된 뒤 원복 완료(정정)

최초 작성 시점에는 `config/tools.config.json` 이 `server.port:13020→13021`·`viewer.controlToken:""→"LIVETEST"`
로 이미 수정된 채 남아 있어 "확인 필요" 항목으로 남겼었다. 이후 확인된 사실: 이 상태는 **개발 웨이브가 만든 것이
아니라, 리더가 §4-② 의 라이브 검증(포트 13021 서버 기동)을 위해 사용한 것**이었다. 검증이 끝난 뒤
리더가 직접 다음을 확인·원복했다:

- `server.port` → **13020**(마스터가 쓰는 원래 포트, 무접촉 유지)
- `viewer.controlToken` → **`""`**
- **커밋 전 config 무변경 확인됨** — `git diff` 상 HEAD 와 바이트 동일

즉 §4-② 라이브 검증에 쓰였던 임시 상태였고, 지금은 **원복이 완료돼 더 이상 확인 필요 항목이 아니다.**

### 3-4. `x.json`(테스트 부산물로 판명 — 정정)

워크트리 루트에 `{"createdAt":"T","items":[]}` 내용의 `x.json` 이 untracked 상태로 존재한다. 최초 작성

리더 결정 Q1(a)에 따라 이번 범위에서는 **두 라우트 모두** 현행(면제) 유지로 확정했다 — 웹의 관련 UX 와

### ④ `setup.slot.add` 는 artifact 편집이지 주차면 추가가 아니다

리더 결정 Q4 에 따라 이름의 오해를 방지하기 위해 3곳(RPC `note` 2개, `artifactSlotEdit.ts` 파일 머리 주석, `slotAddHandler` doc 주석)에 다음을 명시했다: **`setup.slot.add`/`setup.slot.delete` 는 `data/setup_artifact.json` 의 슬롯 엔트리를 편집할 뿐이며, DB(`slot_setup`)·ROI 정본(`PtzCamRoi.json`)은 건드리지 않는다.** 실제로 "주차면(공간)을 추가"하는 경로는 이미 별도로 승격된 `place.space.add`(read-modify-write) → `slot.roi.sync`(DB 차등 UPDATE)다. 이 둘을 혼동해 배선하면 안 된다.

### ⑤ 슬롯편집 후 `renumber`/`placement` 호출 시 편집이 소실될 수 있다(R10, 코드로 막지 않음)

`POST /mapping/renumber`·`/mapping/placement` 는 `setup_artifact.json` 을 **DB(`slot_setup`)로부터 통째로 재생성**한다(`buildArtifactFromSlotSetup`). 따라서 `setup.slot.add` 로 artifact 에 슬롯을 추가한 뒤 이 두 라우트 중 하나를 호출하면, DB 에는 그 슬롯이 없으므로 **추가분이 조용히 사라진다**. 리더 결정에 따라 이 순서 문제는 **코드로 막지 않는다**(막으면 renumber 자체가 못 돈다) — 대신 슬롯편집 응답의 `warnings[]` 필드와 RPC 카탈로그 `note` 로 호출자에게 알리는 방식을 택했다. `dbSlotCount`(DB 의 슬롯 수)와 `artifact.slots.length`(파일의 슬롯 수)가 다르면 경고 문구가 실린다. 실제로 "add → renumber → artifact 확인"까지 재현 실험을 돌려보지는 않았다 — 코드 독해로 확인한 설계상 사실이다.

### ⑥ ★ D-1(중) — `artifact` 버퍼가 파일 전체를 대체하는 문제(독립 QA 발견 → 이제는 가드로 차단, 정정)

`setup.slot.add`/`delete` 는 리더 결정 Q3 의 설계(`artifact` 호출자 버퍼 + `dryRun`) 그대로였는데, 그 설계가
실제로 뜻하는 바 — "`artifact` 를 주면 그 버퍼가 파일을 **부분 병합이 아니라 통째로 대체**한다" — 가 어디에도
적혀 있지 않았다. 독립 QA 가 재현했다: 파일 2슬롯 상태에서 1슬롯짜리 버퍼로 `dryRun` 없이 커밋하면 파일이
2슬롯으로 유지되지 않고 **버퍼 크기(1슬롯 추가분 포함 2슬롯)로 대체**되며, 그 사이 다른 경로로 추가된
슬롯(`c1p1s2`)은 조용히 사라진다. 설계서의 "이번 4건은 파괴 경로에 아예 진입하지 않는다"(R12)는 서술은
**DB 에는 참이었지만 파일에는 거짓이었다** — DB 쓰기는 실제로 0건이 맞지만(§1-3), artifact 파일 전체가
호출자 버퍼로 치환될 수 있다는 점에서 07-28 이전 라운드의 "wipe" 사고와 같은 계열의 위험이 파일 쪽에
열려 있었다.

**지금은 가드로 차단된 상태다**: `rejectBufferCommit()` 이 `artifact` 제공 + `dryRun!==true` 조합을 zod
검증 직후 **409 / RPC `-32005 CONFLICT`** 로 거부한다. 허용되는 두 조합(`artifact`+`dryRun:true`=계산만 /
`artifact` 없이 커밋=디스크 정본 기준 편집)은 유지되므로 **기능 손실은 없다**. 웹은 항상 `dryRun:true` 로만
호출하므로 **웹 동작에는 무영향**이다. 상세는 구현 문서 §4 참조.

### ⑦ ★ 투어링 partial 상태 — 리더 라이브 검증이 발견 → 수정 완료

리더의 실카(Hucoms 192.168.0.153) 라이브 검증 중, 도달 불가 호스트로 재현했을 때 **28스텝이 전부

## 5. 롤백 방법(웨이브 단위 독립성)

각 웨이브는 설계 단계부터 "독립 커밋 가능"을 조건으로 진행됐고, 다음 순서로 **역순 롤백이 가능**하도록 의존 관계가 잡혀 있다:

- **W4(슬롯편집) 단독 롤백**: `src/setup/artifactSlotEdit.ts` 삭제, `server.ts` 의 슬롯편집 라우트 4개(헤드리스 2 + 뷰어 2)와 관련 핸들러/스키마 제거, `methods.ts` 의 `setup.slot.add/delete` 제거, `web/app.js` 의 `addSlot`/`deleteSelectedSlot` 을 W3 상태로 되돌림. W1~W3 산출물과 **로직 의존이 없다**(W4 는 W1~W3 의 파일을 한 줄도 수정하지 않았다고 각 보고서가 명시).
- **W3(점유판정) 롤백**: `src/domain/occupancyJudge.ts` 삭제(단, `src/capture/onPlaceFilter.ts` 의 `groundBand` 옵셔널 인자는 **하위호환**이라 되돌리지 않아도 무해 — 기본값이 기존과 동일), `captureRoutes.ts` 의 judge-occupancy 라우트 제거, `methods.ts` 의 `slot.occupancy.evaluate` 제거, `web/app.js`/`web/core.js` 를 W2 상태로 되돌림. **W4 가 이 웨이브의 산출물을 참조하지 않으므로**(W4 는 슬롯편집이지 점유판정과 무관) W4 이후에도 W3 만 독립 롤백 가능.
- **W2(투어링) 롤백**: `src/setup/touringPlan.ts`·`src/capture/TourJob.ts`·`src/api/tourRoutes.ts` 삭제, `server.ts`/`index.ts`/`methods.ts` 의 관련 배선 제거, `web/app.js` 의 `runTouringTest` 를 W1 상태로 되돌림. 단 `test/viewerPtzSyncCoverage.test.ts` 의 정규식 수정(`[Ff]etch\(`, R15 조치)은 **W1 의 결함을 고친 것**이라 W2 를 롤백해도 **그대로 유지해야 한다** — 되돌리면 카메라 이동 라우트 커버리지 봉인이 다시 무력화된다.
- **W1(토큰) 롤백**: 가장 광범위하다 — `web/token.js` 삭제 시 `web/app.js`/`web/roimaker.js` 의 `mutFetch` 35곳을 전부 원래 `fetch`로 되돌려야 하고, `src/api/controlGate.ts` 와 `server.ts` 의 등록 1줄도 제거해야 한다. **W2~W4 가 신설한 변이 라우트는 모두 `mutFetch` 를 통해 웹에서 호출되므로, W1 을 롤백하면 그 라우트들의 웹 호출부도 함께 원복하거나 최소한 토큰 미부착 상태로 두어야 한다.** 즉 W1 은 사실상 **가장 마지막에만 롤백 가능**(다른 3웨이브가 W1 의 `mutFetch` 규약을 계승했기 때문).

**결론**: W4 → W3 → W2 → W1 순으로는 각 단계가 독립적으로 롤백 가능하다. 역순(W1 을 먼저 롤백)은 W2~W4 의 웹 배선이 깨지므로 권장하지 않는다.

## 6. 후속 작업 후보

1. **[여전히 최상위, 그러나 범위 축소] 마스터 브라우저 육안 확인** — 라우트·RPC·파일 정합·점유판정 일치는 리더 라이브 검증(§4-②)으로 이미 확인됐다. 남은 것은 화면(폴링 라벨·완료 모달·오버레이 픽셀 동일성·2단계 UX 체감·`localStorage`)뿐이다.
2. **무인증 카메라 이동 라우트 2개(§4-①: `/capture/detect` + `/capture/autocorrect`) 별건 처리 여부 결정** — 막을지, 카탈로그 계약(`mutating:true` 승격) 변경을 별도 라운드로 진행할지 마스터 판단 필요.
3. **사전 실패 2건(§4-③) `points:[]` vs "4점 필수" 모순 해소 방침 결정** — 이번 작업과 무관하지만 memo 대기 항목으로 계속 이월되고 있다.
4. **R10(슬롯편집-renumber 소실, §4-⑤) 실제 재현 테스트 여부 검토** — 현재는 경고 문구만으로 대응하는데, 실사용에서 실제로 소실이 발생하는지 재현 테스트를 만들지 여부.
5. **투어링 `partial` 상태의 라이브 관측(§4-⑦)** — 리더 라이브 검증에서는 정상 완주(28/28)만 재현됐고, 실장비가 실제로 실패를 내는 상황에서 `partial` 이 화면에 뜨는지는 미확인이다. 지금까지의 관측으로는 실장비가 보통 204 를 반환해 `failed:0` 만 재현된다.
6. **D-5(순수 판정 라우트가 capture 잡 의존성에 묶임) 처리 여부** — `POST /capture/slots/judge-occupancy` 가 카메라·DB·파일을 전혀 만지지 않는데도 `captureJob`·`finalizer`·`sqlite`·`capture` 4개 의존성이 전부 주입돼야 등록된다(`registerSlotRoutes` 가 `registerCaptureRoutes` 안에 있어서). `src/index.ts` 는 항상 4개를 주입하므로 **실운영 영향은 0** — 설계 일관성 관점의 기록이며 외과적 변경 원칙상 이번 라운드에서는 손대지 않았다(라우트 이동은 `rpcParity` `known` 목록·T4 검사에 파급되기 때문).
7. **`x.json`(§3-4) 출처는 밝혀졌다** — `test/jobFrameReset.test.ts` 의 테스트 부산물로 확인됐다. 남은 결정은 `.gitignore` 등록 여부뿐.
