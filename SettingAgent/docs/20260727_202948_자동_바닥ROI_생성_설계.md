# 자동 바닥 ROI 생성 설계 — 수동 드로잉 / 시뮬레이터 JSON 대체

작성일: 2026-07-27
대상: SettingAgent (web 정밀수집 · `src/ground` · `src/capture/floorRoi.ts`)
질문: **"내가 툴에서 손으로 그린 2.5×5m 주차면 바닥 사각형을, 웹에서 자동으로 만들어 낼 수 있는가?"**

---

## 0. 결론

**가능하다. 그리고 필요한 수학의 90%가 이미 이 저장소에 구현되어 있다.**

- `src/ground/groundModel.ts` — 주차면 4점 + 알려진 2.5×5.0m → 소실점 → f → 지면평면 (n, d)
- `src/ground/project.ts` — `backprojectToGround` / `projectToPixel` (픽셀 ↔ 지면 미터 왕복)
- `GroundModel.source: 'file' | 'auto'` — **`'auto'` 는 이미 타입에 예약되어 있다**

지금 빠져 있는 것은 수학이 아니라 **부트스트랩 경로 하나**다.
현재 `groundInputs.ts` 는 지면모델의 입력 quad 를 **시뮬레이터가 내보낸 `PtzCamRoi.json`** 에서 가져온다.
즉 "손으로 그린 사각형 → 지면모델" 방향만 있고, 그 역방향인 **"지면모델 → 사각형"** 을 안 쓰고 있다.
역방향은 `project.ts` 로 이미 3줄이면 된다.

---

## 1. 마스터가 그리는 사각형의 정보량은 "슬롯 개수 × 8" 이 아니다

주차면 20개를 그리면 좌표가 160개 생긴다. 하지만 **그 160개 안에 들어 있는 독립 정보는 5~6개뿐**이다.

| 미지수 | 개수 | 성격 |
|---|---|---|
| f (초점거리) | 1 | zoom 의 함수 — 카메라 상수 `fovBaseV` 하나로 환원 |
| n (지면 법선) | 2 | tilt, roll |
| d (카메라 지상고) | 1 | **프리셋 불변량** (카메라는 안 움직인다) |
| 격자 방위 θ | 1 | **프리셋 불변량** (주차장은 안 돈다) |
| 격자 원점 (u₀, v₀) | 2 | 지면 위 평행이동 |
| 슬롯 배치(열·개수·피치) | 이산 | 2.5 / 5.0m 로 고정 |

**160개를 손으로 찍는 것은 6개짜리 답을 160번 중복 인코딩하는 행위다.**
그래서 자동화가 가능하다 — 6개만 확정하면 나머지는 전부 유도된다.
게다가 손으로 찍으면 그 160개가 서로 **일관되지 않는다**(슬롯마다 미세하게 다른 카메라를 암시). 자동 생성은 정의상 완벽히 일관된다.

## 2. 제안 구조 — "주차장 지면좌표계"를 정본으로

현재:
```
시뮬레이터 → PtzCamRoi.json (프리셋 × 슬롯 × 4점 픽셀좌표)  ← 정본(authored)
                        ↓
                    웹 오버레이
```

제안:
```
                    ┌─ 주차장 지면 격자 (미터, 프리셋 무관) ──┐  ← 정본(authored, 6개 숫자)
                    │  slot i → rect(2.5m × 5.0m) @ (u,v,θ) │
                    └────────────────┬───────────────────────┘
                                     │ GroundModel(preset) = f(zoom) + n(tilt,roll) + d
                                     ↓  project.ts::projectToPixel
             프리셋별 바닥 ROI 픽셀 4점 (derived, 캐시)
                                     ↓
                              웹 오버레이 / DB slot_setup.slot_roi
```

핵심 전환: **ROI JSON 은 "저작물(authored)"에서 "파생물(derived)"이 된다.**
프리셋을 추가하거나 zoom 을 바꿔도 다시 그릴 것이 없다 — 투영만 다시 하면 된다.

### 왜 이게 결정론인가
`projectToPixel` 은 순수 함수다. 난수·신경망·프레임 의존이 없다.
같은 `(격자, GroundModel)` → 항상 **비트 단위로 같은** 픽셀 좌표. 조명·날씨·시간과 무관.

## 3. GroundModel 을 어떻게 얻는가 — 3가지 부트스트랩 경로

### 경로 A. 1면 드로잉 부트스트랩 ★ 권장 (가장 현실적)

**마스터가 카메라 1대당 주차면 딱 1개만 그린다.** 그 카메라의 전 프리셋·전 슬롯이 자동으로 나온다.

1. 프리셋 하나에서 잘 보이는 주차면 1개를 그린다 (4점).
2. `estimateGroundVPs` + `focalFromVPs` + `buildGroundPlane` → **f, n, d** 획득.
   - 여기서 얻은 `d`(카메라 지상고)와 `slotBearingDeg`(격자 방위)는 **프리셋 불변량**이다.
     이 사실은 `groundModel.ts` 의 `crossPresetSimilarityChecks` 가 이미 명시적으로 활용하고 있다
     (`D_DEV_REL`, `BEARING_DEV_DEG` 검사).
3. `fovBaseV` = `poolFovBaseV` 로 역산 → 카메라 상수로 저장.
4. **다른 모든 프리셋**: 드로잉 없이
   - `f = focalFromZoom(zoom, fovBaseV)`
   - `n = [0, cos(tilt), sin(tilt)]` ← PTZ tilt 만으로 결정
   - `d = 불변량 재사용`
   → GroundModel 완성.

> `n` 유도의 근거: `groundModel.ts:505` 가 `tiltDeg = asin(n[2])` 로 정의하고 이를 PTZ tilt 와 직접 대조한다.
> 즉 roll=0 가정에서 `n = [0, cos t, sin t]` 가 정확히 그 관계의 역이다.
> roll ≠ 0 인 실카메라는 부트스트랩 드로잉에서 roll 보정각을 1회 추정해 카메라 상수에 포함시킨다.

**비용: 카메라당 사각형 1개. 산출: 전 프리셋 전 슬롯.**

### 경로 B. 무드로잉 (실측 기반)

드로잉조차 없이 가능하다. 필요한 값 3개:
- `fovBaseV` ← `packages/lens-calib` 의 렌즈 캘리브레이션에서 획득 (이미 구현됨)
- `tilt`, `zoom` ← PTZ 가 보고
- `d` (카메라 설치 높이) ← **줄자로 1회 실측** (예: 6.0m)

이것만으로 `f, n, d` 가 전부 채워진다. 남는 미지수는 격자의 **원점·방위 3개**뿐이고, 그것은 §4 에서 LPD 가 준다.
정확도는 경로 A보다 낮지만(PTZ 보고값 바이어스가 그대로 들어옴), **드로잉 0** 이라는 장점이 크다.
실전 권장: 경로 B로 초기값 → 경로 A 드로잉 1개로 바이어스 보정.

### 경로 C. 순수 LPD 기반 (드로잉 0, 실측 0)

번호판은 실치수가 알려져 있다(한국 520×110mm). 판 4점 → 그 자체가 metric 스케일 소스다.
LPD 관측을 며칠 누적하면 `buildGroundPlane` 의 입력으로 quad 대신 판 사각형을 쓸 수 있다.
다만 판은 지면이 아니라 **지상 ~0.4~0.6m 의 수직면**이므로 평면 가정이 다르다 —
`ground/contact.ts`(접지 추정)와 엮어야 하고, 경로 A/B 보다 구현 난도가 높다.
**1차 목표로 잡지 말고, 경로 A/B 의 교차검증용으로 쓰는 것을 권한다.**

## 4. 남은 3 자유도(격자 원점·방위) — 여기가 유일한 진짜 문제

`groundModel.ts:540` 의 `§GROUND-SIMILARITY` 주석이 이미 정확하게 경고하고 있다:

> 남는 2 자유도(지면 평행이동)는 **이미지 증거(노면 도색) 없이는 원리적으로 검출 불가** — 한계로 명시한다.

이건 회피할 수 없는 사실이다. 지면 위에서 격자를 통째로 밀어도 `metricErr`·`tiltErr` 는 전혀 안 움직인다.
따라서 원점은 **반드시 이미지에서 관측해야** 한다. 증거 후보:

| 증거 | 이 프로젝트 보유 여부 | 강도 |
|---|---|---|
| **LPD 번호판 중심 누적** | ✅ 이미 수집 중 (discovery) | ★★★ 주 신호 |
| 노면 도색 라인 (LSD/Hough) | ❌ 미구현 | ★★ 보조 |
| 점유 blob 시간누적 | 부분 (occupancy) | ★ 보완 |

### LPD → 원점·방위 유도 (권장)
1. 각 프리셋에서 검출된 번호판 중심을 지면으로 역투영 (`backprojectToGround`, 판 높이 보정 포함).
2. 지면 미터 좌표에 찍힌 점들을 직선 적합 → **방위 θ**.
3. 그 직선 위 점 간격을 2.5m 격자에 **위상 맞춤**(phase fit) → **원점 (u₀, v₀)**.
   - 위상은 1개 자유도짜리 최소화 문제라 매우 안정적이다. 판 5개만 있어도 수렴한다.
4. 격자 인덱스 배정 → 슬롯 번호와 매핑.

**핵심 이득 — 미검출 슬롯이 채워진다.**
메모에 남은 `slot10류 미검출` 문제는 격자가 확정되면 사라진다. 관측이 없는 자리도 격자 외삽으로 좌표가 나온다.
이건 위장이 아니라 기하학적 외삽이므로, `confidence: 'interpolated'` 로 **정직하게 표기**한다
(프로젝트의 "강등 위장 금지" 원칙과 정합).

## 5. 결정론을 강제하는 규칙

이 저장소는 이미 대부분 지키고 있다. 신규 코드에도 동일 적용:

1. **RANSAC 금지.** 최소제곱 + median(로버스트). `buildGroundPlane` 이 이미 `median(ds)` 를 쓴다 — 같은 방식 유지.
2. **집합 순회 순서 고정.** 격자 인덱스 배정 시 `(v, u)` 정렬 키 명시. `Map` 삽입 순서에 의존 금지.
3. **`round5` / `stringify5` 적용** — 프로젝트 규약. 격자 파라미터·GroundModel·픽셀 4점 전부.
4. **골든 해시 테스트.** 고정 입력 → 산출 폴리곤 JSON 해시가 항상 동일함을 vitest 로 봉인.
   이것이 "결정론적이다"의 유일한 증명이다.
5. **자동 재추정 금지.** 격자·GroundModel 은 명시적 트리거로만 갱신. 운영 중 조용히 바뀌면 비결정론이다.
6. **기존 검증기 재사용.** `crossPresetSimilarityChecks` 가 자동 산출 격자에도 그대로 작동한다 —
   자동화가 틀리면 `d` 편차·방위 편차로 즉시 드러난다. **새 검증기를 만들 필요가 없다.**

## 6. 웹 UI 흐름 (정밀수집 페이지)

```
[지면 캘리브레이션]  ← 신규 패널
  1. 프리셋 선택 → 스냅샷
  2. [기준 주차면 1개 그리기]  (기존 드로잉 툴 재사용)
  3. [지면모델 추정]  → f / tilt / 카메라고 d / 방위 표시 + issues 경고
  4. [격자 자동 생성]  → 행 수 · 열 수 · 시작 슬롯번호 입력
  5. 미리보기 오버레이 (자동 ROI vs 파일 ROI 겹쳐 보기 · IoU 표시)
  6. [전 프리셋 적용]  → 각 프리셋 PTZ 로 투영, 드로잉 없음
  7. [DB 저장]  → slot_setup.slot_roi (정규화 4점, stringify5)
```

- 6번이 이 설계의 하이라이트다. 프리셋이 10개면 지금은 드로잉 10 × 슬롯수, 이후는 **드로잉 1**.
- 미리보기에서 마스터가 육안으로 승인한 뒤에만 저장 → 자동화가 사람을 밀어내지 않는다.
- 기존 `#roi-floor` / `#roi-db` 토글 체계에 `#roi-auto` 를 추가해 3자 비교가 가능하게 한다.

## 7. 한계 (정직하게)

1. **지면이 평면이어야 한다.** 경사로·요철 주차장은 오차가 누적된다. `metricErr` 가 이를 노출한다.
2. **격자가 규칙적이어야 한다.** 사선 주차·불규칙 배치는 격자 파라미터로 표현이 안 된다
   → 이 경우는 수동 드로잉을 유지하고, 자동은 "규칙 구간"에만 적용한다.
3. **원점은 이미지 증거 없이는 못 잡는다** (§4). LPD 가 한 대도 안 잡히는 프리셋은 자동 원점 불가
   → 인접 프리셋에서 지면좌표로 이어받거나, 그 프리셋만 수동 유지.
4. **프리셋 복귀 오차.** PTZ 반복정밀도가 나쁘면 투영이 수~수십 px 밀린다.
   기준 프레임 정합(ECC/ORB)이 별도로 필요하다 — 이건 이 설계의 범위 밖 선행과제.
5. **roll ≠ 0.** PTZ tilt 만으로 `n` 을 세우는 경로 B는 roll 을 못 잡는다. 경로 A 부트스트랩으로 1회 보정 필수.

## 8. 단계별 실행 계획 (goal/loop B 모드 권장)

| 단계 | 내용 | 검증 기준 |
|---|---|---|
| **1** | `PtzCamRoi.json` 의 기존 quad → GroundModel → **역투영으로 원래 quad 재생성** | 재생성 quad 가 원본과 평균 IoU ≥ 0.95. **여기서 실패하면 이후 전부 무의미** |
| **2** | 지면 미터 격자 자료구조 + `gridToPixelQuads(grid, model)` | 순수함수 유닛테스트 · 골든 해시 고정 |
| **3** | 경로 A 부트스트랩 라우트 (1면 → 카메라 상수 `fovBaseV`/`d`/`θ`) | 전 프리셋 `dDevRel` < 10%, `bearingDevDeg` < 8° (기존 검사 통과) |
| **4** | LPD 누적 → 격자 원점·방위 위상 적합 | 판 보유 슬롯의 자동 ROI 가 판 중심을 포함 (포함률 100%) |
| **5** | 웹 UI 패널 + 자동/파일 비교 오버레이 | 실카 스냅샷 육안 확인 (sharp 스샷) |
| **6** | DB 저장 경로 + `source:'auto'` 표기 | `slot_setup` 왕복 · 기존 파일 모드 회귀 0 |

**1단계가 결정적이다.** 기존 시뮬레이터 ROI 를 지면모델로 압축했다가 되펼쳤을 때 원본이 복원되면,
"손 드로잉은 6개 숫자의 중복 인코딩"이라는 이 설계의 전제가 실측으로 증명된다.
복원이 안 되면 전제가 틀린 것이므로 즉시 재설계해야 한다. **1단계를 첫 loop 의 성공기준으로 삼을 것.**

| `packages/lens-calib` | 소비자 추가 | `fovBaseV` 공급원으로 승격. 렌즈 왜곡 보정 적용 여부와 좌표계 일치 확인 필수 |
| DB `slot_setup` | 스키마 변경 없음 | `slot_roi` 컬럼 재사용. 출처 구분이 필요하면 별도 컬럼 검토 |

**가장 큰 리스크:** `floorRoi.ts` 의 LLM 경로와 자동 격자 경로가 **동시에 slot_roi 를 쓴다**는 점.
어느 쪽이 정본인지 명시적으로 정하지 않으면 조용히 서로를 덮어쓴다. 구현 전에 우선순위를 확정할 것.
