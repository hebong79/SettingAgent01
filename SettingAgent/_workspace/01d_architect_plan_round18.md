### 2-2. 대체 규칙 — **"내부 구멍은 보간, 바깥은 외삽 금지"**

이것이 마스터 질문("가림으로 생긴 구멍과 행의 끝을 어떻게 구분하나")의 답이다.

> **구멍은 양쪽에서 증거로 둘러싸인 구간이다(= 보간). 행의 끝 너머는 한쪽에서만 증거가 있다(= 외삽).**
> 보간은 근거가 있고 외삽은 없다. 이 한 줄이 규칙의 전부다.

구체 절차 (`fitRowGridOnce` 안, 현행 `kept` 산출 직후):

1. `kept` = `built.quads` 중 `sup.near >= opts.extendMinNearSupport` 인 칸 (**현행 그대로, :278 무변경**).
2. `kept` 를 `latticeIndex` 오름차순으로 보고, **연속 run** 으로 자른다.
   - 인접한 두 kept 칸의 인덱스 차가 `≤ opts.maxGap + 1` 이면 같은 run(= 사이의 결손은 **가림**).
   - 차가 그보다 크면 run 을 **끊는다**(= 행의 끝).
   - `opts.maxGap` 은 기존 값 3 을 그대로 쓴다. **새 튜닝 파라미터를 만들지 않는다.**
3. run 내부의 결손 칸을 **채운다** — `built.quads` 에 이미 있는 그 인덱스의 quad 를 되살린다.
   (격자는 이미 세워져 있으므로 새 좌표를 지어내지 않는다. 도색 지지만 없는 칸이다.)
   채운 인덱스를 `filledIndices` 에 **전부 기록**한다 — 증거 없이 산출한 quad 임을 응답에서 숨기지 않는다.
4. run 이 여럿이면 `sum(near) ` 최대인 run 을 이 위상의 창으로 삼는다(현행 `bestSum` 선택 논리와 동형).
5. 창의 양 끝 밖으로는 **한 칸도 확장하지 않는다.**

### 3-3. 행 간 중복 제거

**어디서 중복이 나는가** — 서로 다른 전방선 후보 2개가 같은 물리 행에 latch 하는 경우.
(`fitRowGridOnce` 는 근/원변 양방향 `frames` 를 이미 내부에서 겨뤄 **후보당 1건**만 내므로,
깊이 뒤집힘 중복은 여기서 생기지 않는다.)

**병합 판정 — quad 집합 겹침 단일 기준** (새 기하 수식 0줄, `quadIoU` 재사용 = R4):
- 두 행 A(점수 높음)·B 에 대해, B 의 각 quad 가 A 의 어떤 quad 와 `quadIoU ≥ opts.rowMergeIoU` 인지 센다.
- 그 비율이 `≥ 0.5` 면 **같은 행**으로 보고 B 를 버린다(A 유지).
- `opts.rowMergeIoU` 기본 **0.5**. 새 튜닝 파라미터이지만 임계가 아니다 — 같은 행이면 0.9 대, 다른 행이면 0 대로 갈린다(측정으로 확인 필요, §6-4).

**F-b(연속 가림 4칸 이상) 대응 — 조각난 같은 행의 재결합:**
- 두 행의 전방선 각도 차 `< 1°` **그리고** 격자 위상 차가 `2.5m` 주기로 `< 0.25m` 이면 **같은 행의 조각**으로 보고
  `issues` 에 `"행 조각 의심: cand#i ↔ cand#j"` 로 **기록만** 한다.
- **자동 병합하지 않는다.** 자동 결합은 두 개의 진짜 이웃 행(같은 도색 방향·같은 위상)을 하나로 붙일 수 있고,
  그건 반증목록의 "거리 하드 게이트"가 죽은 것과 같은 종류의 실패다. 판단을 사람/상위에 남긴다.

### 3-4. 정렬 기준과 **`rows` 를 만드는 정확한 위치**

```
:472   const scoredCands = [];
:473~478   … 후보별 fitRowGrid …
──────── ★ 여기서 rows 를 만든다 (거리 게이트 **앞**) ────────
       const rows = dedupeRows(scoredCands.map(e => e.r))
                      .sort(by paint.score desc → quads.length desc → 순회 인덱스 asc);
:480   let pool = scoredCands;              ← 이하 전부 현행 그대로
:481~488  거리 게이트
:489~494  argmax → best
```

**거리 게이트(`maxRowDistanceRatio`) 앞에 두는 이유**: 게이트는 "먼 행을 **버리는**" 장치다.
①("보이는 모든 면")은 먼 행도 찾아야 하므로 `rows` 가 게이트를 통과하면 안 된다.
현재 기본값은 `0`(비활성)이라 실측상 차이는 없지만, **의미상 위치가 이게 맞다.**

**정렬키에서 `effectiveScore` 를 쓰지 않는다** — `effectiveScore` 에는 `aimCenterWeight` 가 곱해져 있어
"중앙에 있는 행"이 위로 올라온다. 사람이 읽는 목록의 1등이 도색 증거가 아니라 조준으로 정해지면
서열 규약("도색 증거가 1순위, 중심성은 동점 해소자")이 목록에서 역전된다.
→ `rows` 정렬은 **`paint.score`**, 각 원소에 `effectiveScore` 도 그대로 실어 둘 다 보이게 한다.

### 3-5. `aimCenterWeight`(1.6) · `maxRowDistanceRatio` — **끄지 않는다. 역할을 좁힌다**

마스터가 정확히 물은 지점이다. 답:

| 항목 | 결정 | 근거 |
|---|---|---|
| `aimCenterWeight = 1.6` | **값 불변. `best` 선택에만 작용하도록 역할을 축소** | ① F12/U4 는 24관측 LOPO 4폴드 전부 통과한 **「검증됨」** 등급이다. 근거 없이 버리면 그 검증을 폐기하는 것이다. ② `best` 는 여전히 필요하다 — 소비자 10곳 전부가 `.best` 를 읽고, `slot.roi.sync`/`apply` 가 소비할 단일 행이 있어야 한다. 다중 행 모드에서 그 역할이 **"이 프리셋이 겨눈 대표 행" 지정자**로 명확해진다 |
| `rows` 정렬 | **aim 항 배제**(§3-4) | 목록의 서열은 도색 증거로 정한다 |
| `maxRowDistanceRatio` | **0 유지(비활성). `rows` 에는 원리적으로 미적용** | 기본이 이미 0이라 실측 무변화. 켜면 `rows` 에서 먼 행을 지워 ① 을 정면으로 깨므로 적용 지점을 `pool`(=`best` 전용)로 **구조적으로 고정** |

> 요약: **`best` = 조준·거리까지 고려한 대표 행 / `rows` = 도색 증거 기준 전체 행.** 두 개의 다른 질문에 두 개의 답.

## 11. ★ 설계 정정 — §2-3 의 `:314` denom 변경을 **철회한다** (구현자 실측 반증)

- 계기: `dev-r18` 이 §6-6 정지조건에 걸려 보고. 골든 v1 · 1:1 프레임 `ceaaed722663` · d0.

### 11-1. 무엇이 틀렸나

§2-3 은 *"커버리지 항의 취지는 `inFrameCells` 만으로 온전히 표현되고 정답지 성분만 빠진다"* 고 주장했다.
**실측이 이를 반증한다.** `inFrameCells`(`bayGrid.ts:309~313`)는 `scored` = 그 위상의 `kFrom..kTo` 전 칸에서 센다.
`kFrom`/`kTo` 는 `phase` 의 함수이므로 **`inFrameCells` 자체가 위상 의존 자유변수**다.
`min(expectedBays, ·)` 클램프가 지금까지 이 병리를 **가려 왔다** — 정답 격자도 상한에 걸려 1.0 을 받았다.

| | phase(m) | quads | paint.score | inFrameCells | coverage | effective |
|---|---|---|---|---|---|---|
| expected(정답 격자) | 10.42370 | −4..−1 | 0.8958 | 5 | **1.0**(클램프) | 1.98510 |
| evidence(같은 격자) | 10.42370 | −4..−1 | 0.8958 | 5 | **0.8** | 1.588 |

그리고 **재현율은 두 모드 동일(17/41)** — 이 변경은 ① 을 1면도 못 올리고 위치정확도만 깎았다.

### 11-2. 결정 — **3안(이번 라운드 `:314` 무변경)**

`bayGrid.ts:314` 를 **현행 그대로** 둔다. `rowExtentMode` 는 **창 선택 규칙(run)만** 바꾼다.

근거:
1. **이득 0 · 손실 0.21.** 재현율이 두 모드 동일이므로 목표 ① 에 기여가 없다.
2. **변수 격리.** A(창 규칙)·B(다중 행)·C(채점)의 효과를 denom 병리가 오염하면 이 라운드 결론 전체를 못 읽는다.
3. **2안(denom = run 범위)은 반증목록 위반이다.** 구멍 보간으로 `quads.length = hi−lo+1` 이 보장되므로
   `denom` 을 run 범위로 좁히면 **coverage 가 항상 정확히 1.0** 이 된다 = `coverageExponent=0` 과 동치.
   반증목록: *"페널티 제거하면 `2:1` 이 0.109 로 붕괴"*. **재시도 금지 대상이다.**
4. **1안(그대로 진행)은 §6-6 을 스스로 어기는 것**이고, 원인이 규명된 회귀를 산출로 포장하는 것이다.

**잔여 누출 명시**: `expectedBays` 가 커버리지 항에 남아 목표 ① 의 "개수 무사용"은 **부분 달성**이다.
단 그 누출은 **산출 집합(어느 칸을 내보내는가)** 이 아니라 **순위(어느 위상이 이기는가)** 에만 작용하고,
이 씬에서 재현율에 0 영향임이 실측(17/41 동일)으로 확인됐다. **숨기지 말고 이 문장 그대로 보고한다.**

### 11-3. 다음 라운드 표적 — **4안: 위상 불변 분모** (2안이 아니다)

```ts
// denom 을 위상 함수에서 빼낸다. spanLo/spanHi 는 :256~261 에서 phase 루프 **밖**에서 계산된다
// (evid = 검출 코너의 폭좌표 · endA/endB = 전방선의 이미지 클립 끝점) → 위상 불변이다.
```

- **위상 불변** → 같은 전방선의 두 격자가 같은 분모를 받는다 → `1:2` 는 `paint.score`(0.8958 vs 0.7637)로 갈려 정답이 이긴다.
- **정답지 무사용** → ① 완전 달성.
- **"짧은 조각" 방어 유지** → 가시 행 폭 10칸에 2칸만 세운 후보는 0.2 를 받는다. 2안처럼 항이 죽지 않는다.
- **위험**: 지평선 근처에서 `spanHi−spanLo` 가 발산해 분모가 커지면 먼 행이 일괄 강등된다.
  `maxRowCells` 클램프로 상한을 두되 **측정 전에는 채택하지 않는다.**

**채택 판정 규칙(구현자가 추가 왕복 없이 실행 가능):** 아래 3개를 **전부** 만족하면 4안 채택, 하나라도 실패하면 3안 유지.
1. `1:2` 정본 대비 IoU **≥ 0.95373**(expected 모드 값 회복)
2. `1:1`·`2:1`·`2:2` 정본 대비 IoU 가 expected 모드 대비 **±0.002 이내**
3. 재현율 **≥ 17/41**, 정밀도 하락 **없음**

3. **1:3 이 가장 병적이다** — 가시 2면 · `detectable 0/2` 인데 5행 통과, 정밀도 0.0.

### 12-3b. 19회차 측정·설계 방향 (수정판)

**측정 1 — 두 축을 같이 찍는다.** 후보별 `paint.score` · `paint.near` · **`quads.length`** 를 한 표에.
길이 축에 골짜기가 있는지가 1순위 확인 대상이다.

**측정 2 — `1:3` 최소 사례 해부.**

★ **"5행이 `near ≥ 0.5` 를 통과한다"는 로그 추론이 아니라 코드로 보장된다** — `bayGrid.ts:368`
`if (paint.near < opts.minNearSupport) continue;` 가 구조적 게이트이므로 `rows` 에 들어온 모든 행은
**필연적으로 `paint.near ≥ 0.5`** 다. (구현자가 "로그에 `paint.near` 가 없어 미측정"이라 했는데,
이 항목은 로그가 아니라 **제어흐름에서 나온다.** 다만 그 지적 덕에 아래 구분이 분명해졌다.)

→ **그래서 다음 역전이 지금 이미 확정 사실이다.**

★ **문장을 정밀하게 적는다** — 두 수치는 **산출 단위가 다르다**(구현자 정정, `bayGeometry.ts:655` `near/k` 로 확인):

| | 산출 단위 | 임계 |
|---|---|---|
| 정답 면 `detectable` | **quad 1개**(`quadPaintSupport([단일 quad])`, k=1) | `extendMinNearSupport` = **0.35** |
| 행 `paint.near` | **그 행 quad 들의 평균**(`near / k`) | `minNearSupport` = **0.5** |

> **`1:3` 에서 정답 2면은 개별 `near < 0.35` 인데, 오검출 5행은 행 평균 `near ≥ 0.5` 다.**
> **진짜 주차면이 가짜 행보다 도색 지지를 낮게 받는다.**

결론은 그대로 성립하고 **오히려 강해진다** — 개별 0.35 도 못 넘는 정답이 평균 0.5 를 넘는 가짜와 겨루고 있다.
⚠ **"오검출 행의 *모든 칸*이 `near ≥ 0.5`" 로 읽으면 안 된다.** 평균이 0.5 를 넘어도 개별 칸은 그 아래일 수 있다.
이 구분이 대책을 가른다 — **개별 칸 게이트냐 행 평균 게이트냐.** 재인용 시 이 표를 함께 옮겨라.

→ ★ 문턱 문제가 아니라 **`quadPaintSupport` 의 측정 타당성 문제**라는 가설의 직접 근거다.
**문턱을 올리면 진짜 행이 먼저 죽는다.** 임계 튜닝으로 덮지 마라.

**여전히 미측정인 것(로그 추가 필요)**: `near` 의 **실제 값**(0.51 인가 0.95 인가)과
`score = near·1.0 + side·0.5 + far·0.3` 의 **3분해**. `score` 에서 `near` 를 역산할 수 없다.
→ `roiAutoRecall.ts` 로그에 `near/side/far` 3분해 추가. **역산으로 채우지 마라.**

**측정 3 — dedup 전후 분해.** 현재 로그는 dedup **후**만 있다. 상한만 말할 수 있다
(5뷰 × `frontCandidates=8` = 40 → 33 이므로 dedup + `fitRowGrid` 실패가 **합쳐서 최대 7개**).
둘의 분해는 미측정. `roiAutoRecall.ts` 로그에 **`tried.length` 한 줄** 추가로 나온다.

**설계 가설(측정 후 판정) — `rows` 진입/정렬에 길이 압력을 넣되 N 은 안 쓴다:**

§3-4 는 `rows` 를 `paint.score` 로 정렬하고 길이를 2순위 tie-break 로 뒀다. **그 tie-break 은 죽어 있다** —
`paint.score` 부동소수 동률이 나지 않으므로 길이 축은 한 번도 발화하지 않았다(구현자 확인).

#### 12-3b-① ★ 정정 — 후보 A 와 B 는 **같은 실험**이다 (구현자 실측)

`DEFAULT_BAY_OPTS`: **`phaseFitWeight: 0`** · `coverageExponent: 1`.
따라서 내가 "aim 항만 뺀 `effectiveScore`" 라 부른 식은 실제로 **`paint.score × coverage` 로 축약된다**
(`phaseTerm` 항은 가중 0 이라 통째로 죽어 있다 — **그 이름은 살아 있지 않은 항이 살아 있는 것처럼 읽히므로 폐기한다**).
그리고 `coverage = min(1, quads.length / min(expectedBays, inFrameCells))` 이므로
후보 A 가 현행 정렬에 더하는 **유일한 신호는 `길이 / 분모`** 다. 후보 B(`길이 ≥ 최장행 × r`)와 **같은 축**이고
차이는 정규화 분모뿐이다. → **두 갈래로 재면 같은 실험을 두 번 한다.**

**→ 하나로 합친다: "길이 정규화 분모 후보 목록" 단일 실험.**

| 분모 후보 | N 사용 | 상태 |
|---|---|---|
| `min(expectedBays, inFrameCells)` (현행) | **사용** | ① 출력 집합에 정답지 누출 → `rows` 용으로 부적격 |
| **그 뷰 최장 행의 길이** (구 후보 B) | 안 함 | 미측정. 1:1 에 r=0.5 → 8행→4행 `[7,4,7,6]`(구현자 검산) |
| `inFrameCells` 단독 | 안 함 | **F18 로 기각**(위상 의존) |
| `spanHi−spanLo` 기반 | 안 함 | **F22 로 기각**(행 길이를 대표 못 함) |
| **run 이 덮은 격자 구간의 프레임 안 칸 수** | 안 함 | **미측정.** 구현자가 18회차 2안으로 올렸다가 합의 없이 접은 것 — 구멍 보간 때문에 coverage≡1 이 되는지 **먼저 확인** 필요 |

**`phaseFitWeight` 를 0 이 아닌 값으로 켜는 것은 별개 변경이다** — 4회차 U1 에 *"2:2 는 정답을 밀어주지만
1:2 는 오답을 밀어준다"* 기록이 있다. 이번 실험에 섞지 마라.

**r(또는 어떤 분모든) 을 측정으로 "맞추지" 마라.** 분포에 골짜기가 있을 때만 채택하고,
없으면 게이트가 아니라 **변별자 자체를 다시 찾으라는 신호**로 읽어라.
