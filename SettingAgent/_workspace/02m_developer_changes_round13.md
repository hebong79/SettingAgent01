## 1. ★ P0 — JPEG 압축 가설 반증

`cam.capturePNG`(무손실)로 **같은 PTZ** 에서 프레임을 다시 받아 동일 지점의 드리프트를 쟀다.
(PNG 2651~2891KB vs JPEG 456~498KB — 실제로 무손실이 맞다.)

| key | 추정기 | **JPEG 드리프트** | **PNG 드리프트** | 판정 |
|---|---|---|---|---|
| **1:1** | 파이프라인 `stripeCenter` | 1.24px | **1.49px** | **증가** |
| | 자체(±22px) | 1.11px | 1.49px | 증가 |
| | 비례창 | 1.17px | 1.43px | 증가 |
| | 수동 `tM` | 0.96px | 1.23px | 증가 |
| **2:1** | 파이프라인 `stripeCenter` | −1.30px | **−0.96px** | 감소 |
| | 자체(±22px) | −1.26px | −1.03px | 감소 |
| | 비례창 | −1.26px | −1.03px | 감소 |
| | 수동 `tM` | −1.06px | −0.78px | 감소 |

**압축을 제거해도 드리프트가 사라지지 않는다.** `1:1` 은 오히려 **커졌고**(1.24 → 1.49px), `2:1` 은 줄었다. 방향이 일관되지 않는다 — 압축이 원인이라면 두 프리셋 모두 줄어야 한다.

→ **JPEG 8×8 블록 DCT 인공물 가설 기각.**

### ★ 부수 발견 — 캡처 간 변동성이 신호의 1/4 이다

같은 프리셋·같은 PTZ 인데 두 캡처의 드리프트가 다르다(1:1 1.24 → 1.49, 2:1 −1.30 → −0.96). **0.25~0.34px 의 캡처 간 변동**이며, 자가보정 지상고도 함께 흔들린다(1:1 4.951 → 4.968m, 2:1 4.960 → 4.940m).

신호(≈1.2px) 대비 **20~28% 의 잡음**이다. 이는 별개의 함의를 갖는다:
- 드리프트의 **존재**는 두 캡처 모두에서 확인되므로 실재한다
- 그러나 그 **크기를 1건 캡처로 정밀 추정하는 것은 신뢰할 수 없다**. 앞으로 이 값을 다룰 때는 다중 캡처 평균이 필요하다
- 리더가 8~12회차에 걸쳐 요구한 "수치를 정정하라"의 연장선에서, **11·12회차에 내가 보고한 1.1~1.3px 는 단일 캡처값**임을 명시한다

## 2. P1 — 합의 서비스 배선

### 2-1. 배선 내용

`src/rpc/services/roiAuto.ts` 에 `detectConsensus` 추가:
- 고정 디더 6시점 `[0,0] [-1.5,0] [1.5,0] [0,-0.8] [0,0.8] [1.0,0.6]`(기저가 항상 첫째)
- 각 시점 quad 를 지면 역투영 → **기저 시점 좌표로 역회전**(`R_x(−dtilt)` 후 `R_n0(+dpan)`) → 행 중심 2.0m 이내 군집
- 최다 득표 → **동점 시 기저 우선 → 낮은 인덱스**(결정론)
- 한 시점이 실패해도 전체를 막지 않는다. `t.ptz` 가 없으면 단일 시점으로 물러선다
- **3개 라우트 전부**(`detect`/`score`/`apply`) 합의 경로를 탄다. `consensus: false` 로 끌 수 있다

카탈로그 note 갱신(리더 지시): `roi.auto.detect`·`roi.auto.score` 에 **"고정 디더 6시점 촬영 — 카메라 점유·소요시간 6배(프리셋당 약 70초)"** 명시.

### 2-2. ★ 라이브 검증 미완 (정직 표기)

**배선 후 전 프리셋 재측정을 하지 못했다.**
실행 중인 SettingAgent(13021)가 `roi.auto.*` 등록 **이전 빌드**로 떠 있어 `알 수 없는 method: roi.auto.score` 를 반환한다. **마스터가 쓰고 있는 프로세스를 임의 재시작하지 않았다.**

따라서 현재 상태는:
- 코드·타입·유닛테스트: **통과**(281파일 3552테스트 green, `tsc` exit 0)
- 도구 레벨 합의 수치(12회차): `2:2` 0.00000 → **0.94410**, 평균 0.56883 → 0.75668
- **서비스 경로에서의 동일성 확인: 미완**

리더가 요구한 "배선 후 전 프리셋 재측정해 도구 레벨 수치와 일치하는지 확인"은 **다음 라운드로 넘어간다**. 서버 재시작 승인이 필요하다.

## 8. 14회차 권고

1. **★ U1 먼저 — 서버 재시작 승인을 받아 합의를 라이브로 확인하라.** 코드는 들어갔지만 **아직 산출물이 아니다**. 도구 레벨 `2:2 = 0.94410` 이 서비스 경로에서 재현되는지 확인해야 완결된다.
2. **★ U4(캡처 변동)를 먼저 정량화한 뒤 드리프트를 다시 논하라.** 같은 PTZ 두 캡처에서 드리프트가 1.24 → 1.49px 로 변했다. **잡음이 신호의 1/4** 이면 단일 캡처 기반 결론은 위태롭다. 같은 PTZ 로 5~10회 캡처해 드리프트의 평균·표준편차를 내면, 남은 "지면 비평면" 후보를 검증할 기준선도 함께 생긴다.
3. **12종 제거 후 남은 것이 약하다는 사실을 직시하라.** 단일 원인 탐색을 계속할지, **누적 오차 모델**로 전환할지 판단이 필요하다. 후자면 "10면을 0.98 위로"라는 목표 자체의 달성 가능성을 재평가해야 한다 — 목표를 낮추자는 게 아니라, **관측 잡음이 0.25px 인데 0.98 이 요구하는 정밀도가 그보다 빡빡한지** 먼저 계산해 보자는 것이다.
4. **마스터 보고:** "**JPEG 압축 가설도 반증**됐습니다 — 무손실 PNG 에서 드리프트가 그대로거나 오히려 커집니다. 후보 12종이 제거되고 남은 하나(지면 비평면)도 약합니다. 대신 **같은 PTZ 재촬영 시 드리프트가 1.24→1.49px 로 변한다**는 걸 발견했습니다 — 관측 잡음이 신호의 1/4 이라, 단일 원인을 더 찾기 전에 **잡음 바닥을 먼저 재야** 합니다. `2:2` 합의는 서비스에 배선했으나 실행 중인 서버가 구버전이라 **라이브 확인은 재시작 승인이 필요**합니다."
