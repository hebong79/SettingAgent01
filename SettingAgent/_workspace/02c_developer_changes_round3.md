## 2. 구현한 것

### P1. 지면모델 주입 — `focalFromVPs`·VP_d 추정을 자동 경로에서 **제거**

| 신규 파일 | 내용 |
|---|---|
| `src/ground/cameraIntrinsics.ts` | **인터페이스 우선**. `PresetIntrinsics{fovDeg, fovAxis, tiltDeg, heightM, imgW, imgH, source}` · `CameraIntrinsicsProvider` · `focalPxOf` · `groundModelFromIntrinsics` · `chainProviders` · `staticProvider` · **`lensCalibrationProvider`(실카)** |
| `src/ground/placeMetaIntrinsics.ts` | 시뮬 로더. **주차면을 담을 필드가 없는 타입**만 반환 |

리더 지시대로 **인터페이스를 먼저 만들고 구현을 끼웠다**. 실카 공급자(`lensCalibrationProvider`)는 `lens_calibration.json` 의 `zoomHfov` 13점 표를 선형보간하고 PTZ tilt·설정 설치고를 받는다 — 시뮬 공급자와 **같은 인터페이스**를 만족하며 테스트로 봉인했다(R10: 시뮬 전용 경로 금지).

`fov` 축 구분을 명시적으로 뒀다: Unity `fieldOfView` 는 **수직**(→ `imgH` 로 환산), RTSP `zoomHfov` 는 **수평**(→ `imgW`). 검산: cam1:p1 fov 20.86546° → f = 540/tan(10.4327°) = **2932.8px**, 리더 예측과 일치.

**hold-out 구조 봉인(P1 지시):** `readPlaceMeta` 는 `parking_spaces` 를 **읽지도 복사하지도 않는다**. 테스트 2건으로 못 박았다 — ① 반환 구조 JSON 에 `parking_spaces`/`points`/`idx` 문자열이 0건 ② 소스 코드(주석 제외)에 `parking_spaces`·`PlaceRoiSpace`·`normalizePtzCamRoi` 0건.

### P2. 이미지가 공급하는 3 자유도만 — `src/ground/bayGrid.ts`

```
① 행 방향   ← 검출 근변선을 지면으로 역투영(rowFrameFromLine)
② 격자 위상 ← 검출 근변 코너의 폭방향 좌표(widthCoordOf)
③ 나머지    ← 폭 2.5m · 깊이 5.0m 상수
```

**소실점을 구하지 않는다.** 격자 간격이 상수이므로 적합할 파라미터가 **위상 1개**뿐이다 — 사영 1D 적합도, 이면군 탐색도, 격자 잔차 게이트도 사라졌다. 위상 후보는 ① 검출 코너들 ② 균등 스윕(40분할)이고 고정 순서 전수 순회다(난수 0).

### P3. 도색지지(P1 점수)는 유지, 역할 변경

선택 1순위 키로 유지하되 고르는 대상이 "f·VP 조합"에서 **"어느 근변선 · 어느 위상"** 으로 바뀌었다. 탐색공간이 프리셋당 수천 가설 → **8 후보 × 48 위상**으로 줄었다. 속도도 24~39초 → **11~15초**로 개선됐다.

**격자확장과 함께 나갔다**(리더 지시): 격자는 검출 코너 스팬을 덮도록 생성되고 칸별 근변 지지로 개별 검증된다. 여기에 **커버리지 가중**을 추가했다 — 기대 베이 N칸 중 몇 칸을 세웠는지로 점수를 깎는다(없으면 "도색 위의 짧은 2칸"이 "온전한 4칸"을 이긴다).

### P4. 스케일 — 2.5/5.0 을 쓰고 편차는 보고만

리더 실측 +1.0%(폭 2.525m·깊이 5.051m, 비율 정확히 2.000)를 **억지로 맞추지 않았다.** `slotWidthM=2.5` · `slotDepthM=5.0` 상수를 그대로 쓴다. 이 1.0% 는 시뮬 고유값일 수 있고 실카 재확인 대상이다. 결과 IoU 0.89~0.96 의 일부는 이 스케일 차이에서 온다(§4-2).

### 부수 수정 — 내가 만든 집계 버그

`summarize` 가 `D10_ANCHOR_DEFECT` 라벨이 붙은 면까지 평균에서 제외하고 있었다. 그래서 **1:1 평균이 0.94021 인데 요약이 `meanIoU: 0` 을 찍었다.** 숫자를 숨기는 집계였다.
→ 집계 제외는 **구조적 제외**(D8 4점 아님 · D9 슬롯24)뿐으로 고쳤다. D10 은 라벨이지 제외가 아니다.

또 `placeMetaProvider` 가 **없는 프리셋에도 카메라 기본값으로 제원을 지어내던** 결함을 테스트로 잡아 고쳤다(프리셋 부재 → null).

### 4-2. `1:1`·`2:1` — 0.98 에 못 미치는 잔차

13면이 0.89~0.96 에 몰려 있고 프리셋 안에서 단조 경향을 보인다(2:1 은 s14 0.891 → s19 0.966). 계통 오차다. 후보 원인 2개:

1. **스케일 +1.0%**(리더 실측). 2.5m 대신 2.525m 가 참값이면 격자가 누적으로 어긋난다 — 단조 경향과 부합한다. P4 지시대로 **맞추지 않았다.**
2. **위상 잔차** 0.696~0.725m — 검출 코너와 채택 격자 경계의 median 차이. 슬롯 폭 2.5m 의 28% 다. 위상 스윕이 40분할(0.0625m)이므로 해상도 문제는 아니고, **선택된 위상이 검출 코너와 잘 안 맞는다**는 뜻이다.

**어느 쪽인지 확정하지 못했다**(§5-U2). 스케일을 2.525 로 바꿔 보면 즉시 갈리지만 P4 금지사항이라 하지 않았다.

### 4-3. 시도했으나 효과 없던 것 (정직 기록)

**검출 긴 도색선이 근변인지 원변인지 모르므로 깊이 방향 양쪽을 다 시도**하도록 `fitRowGrid` 에 `frames = [+v, −v]` 를 넣었다. 근거는 "2:2 는 원변선을 골랐으니 그 선에서 카메라 쪽으로 뻗으면 정답"이었다.
**결과: 전 프리셋 수치 무변화.** −v 변형이 한 번도 이기지 못했다 → 채택된 오답 선들은 **이 행의 원변선이 아니라 무관한 다른 도색선**이다. 코드는 남겼다(비용 없음, 다른 장면에서 필요할 수 있음).

## 8. 4회차 권고

1. **★ U1 — 근변선 선택.** 도색지지만으로는 "어느 도색선이 이 행의 근변인가"를 못 가른다(오답도 진짜 도색선이다). 남은 미사용 증거는 **분리선 스텁의 위치**다 — 정답 행에서는 검출 코너가 격자 경계에 몰리고(위상적합 작음), 오답 행에서는 흩어진다. 2:2 실측이 그 방향을 지지한다(정답 rank1 0.485m vs 오답 rank2 0.667m). **`phaseFitM` 을 선택 점수에 넣어라** — 지금은 tie-break 로만 쓴다. 값싸고 되돌리기 쉽다.
2. **U2 — 스케일 vs 위상 분리.** `slotWidthM` 을 2.525 로 **한 번만** 돌려 보면 즉시 갈린다. IoU 가 0.94 → 0.98 대로 오르면 스케일이 원인이고, 안 움직이면 위상이다. **P4 금지 때문에 하지 않았으니 리더 승인 필요.**
3. **U4 — D10 판정식.** "자동 근변이 도색 위에 있다(근변지지 높음) **그리고** 수동 변이 도색선에서 이탈"로 좁혀야 한다. 지금은 후자만 본다.
4. **U9 — 구 경로 정리.** `detectBaysPaired`·`detectBays` 는 자동 경로에서 죽었다. 유지할지 삭제할지 결정 필요(내 판단으로는 삭제해도 무방하나 **기존 데드 코드 삭제 금지 규칙**에 걸려 손대지 않았다).
