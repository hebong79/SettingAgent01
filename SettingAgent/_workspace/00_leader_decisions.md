## D-0. 선행 블로커 해소 — U1(프레임 취득 시임) **해결됨. 구현자는 조사하지 말 것.**

설계자가 "구현 착수 전 1순위 확인"으로 남긴 U1 을 리더가 직접 추적해 확정했다.

```
src/index.ts:47        new RpcCameraClient({ rpc, cameraCfg, cameraposFile })
src/clients/RpcCameraClient.ts:55  requestImage(camIdx, presetIdx, ptz?)
   ├─ ptz 있으면  rpc.callRpc('cam.setPTZ',    { camId, pan, tilt, zoom })
   └─ 항상        rpc.callRpc('cam.captureJPG',{ camId })  → { img_bytes: base64 }
                  → CapturedImage.jpg : Buffer
```

- **쓸 시임:** `ICameraClient.requestImage(camIdx, presetIdx, ptz?)` → `.jpg`(Buffer) → `sharp(jpg).greyscale().raw()` (기존 `captureRoutes.ts:220 jpegToGray` 와 동일 패턴)
- **레거시 주의:** `src/clients/CameraClient.ts` 의 `POST /req_img` 경로는 **현재 유니티 빌드에 없다.** 리더가 실측: `curl -X POST http://localhost:13110/req_img` → `404 알 수 없는 엔드포인트: /req_img`. 이 클래스를 쓰지 마라.
- 리더가 이 경로(`cam.setPTZ`→`cam.captureJPG`)로 전 5개 프리셋 프레임을 실제로 취득해 동작을 확인했다(1920×1080, Δpan/Δtilt = 0.000).

## D-1 (Q1 회신) — 앵커 결함: **(b) 로 진행하되 (a) 를 준비해 둔다.** 정본은 건드리지 않는다.

설계자 실측: `idx1`·`idx8` 의 수동 앵커가 실제 도색선에서 **9.03px 이탈**(정련 MAD 0.46px, 대비 185 — 확신 있는 검출). 즉 **자동이 맞고 수동이 틀렸다.**

**결정:**
1. **정본을 수정하지 않는다.** 마스터 부재중 정본 교정은 리더 권한 밖이다. (a) 는 정본 쓰기를 수반하므로 지금 실행하지 않는다.
2. 채점은 **두 기준을 모두 산출**해 응답·보고서에 병기한다:
   - `iouVsManual` — 현재 수동 정본 대비 (마스터가 말한 98% 의 문자 그대로의 기준)
   - `iouVsPaint` — 검출된 도색선 대비 (물리적 정답)
3. `idx1`·`idx8` 은 `D10_ANCHOR_DEFECT` 로 분류하고 **이탈 px 수치를 근거로 첨부**한다. 통과 집계에서는 빼되 **은닉하지 않는다** — "제외했음 + 사유 + 수치"를 표에 남긴다.
4. **(a) 를 즉시 실행 가능한 상태로 준비한다.** 교정된 앵커 4점을 `_workspace/` 에 미리보기로 산출해 두고, 마스터가 승인하면 `roi.auto.apply` 한 번으로 반영되게 한다.

**근거:** 설계자 (c) 분석이 정확하다 — 수동을 고수하면 목표 달성은 자동을 일부러 틀리게 만드는 것과 같고 그것은 위장이다. 그렇다고 부재중에 정본을 덮으면 되돌리기 비용이 크다. **"측정은 양쪽 다, 변경은 승인 후"** 가 유일하게 정직하면서 되돌릴 수 있는 선택이다.

> 마스터 복귀 시 보고할 문장: "98% 는 21면에서 달성했고, 2면은 **수동 정본이 도색선에서 9.03px 틀려서** 미달로 잡힙니다. 교정본을 준비해 뒀으니 승인만 주시면 됩니다."

## D-2 (Q2 회신) — **승인.** `1:3`(2면)은 `D1_TOO_FEW_BAYS`

`graded:false` 로 표기하고 통과·평균 집계에서 제외한다. 리더 컨텍스트 §6 판단과 일치한다.
단 **"제외 = 통과"로 읽히지 않게** 보고서에 `검증 불가(2면, 사영 1D 적합 불가)` 로 명시한다.

## D-3 (Q3 회신) — 슬롯 24: **제외 유지**(`D9_SLOT24`). 마스터 판단 대기.

파일(cam1:p1 8번째) ↔ DB(cam2:p1 7번째) 불일치가 미해소다. 리더가 임의로 한쪽을 고르면 잘못된 카메라에 기하가 실릴 수 있다.

**추가 근거(리더 실측):** 이 빈 엔트리가 **현재 회귀 실패 2건의 원인**이다(`00_leader_context.md` §5-1). 슬롯 24 를 채우면 기준선이 green 이 된다는 것도 실측으로 확인했다. 즉 이 결정은 데이터 정합성 문제이자 회귀 문제이며, **마스터의 한 번의 판단으로 둘 다 해소**된다.

## D-4 (Q4 회신) — **승인.** `apply` 는 정본 파일만 쓰고 DB 는 기존 `slot.roi.sync` 위임.

설계자 판단이 옳다. `updateSlotRoiGeometry` 의 유일한 호출자가 `roiSlotSync.ts:150` 이므로, DB 쓰기 경로를 신설하지 않는 것이 R5 를 가장 강하게 만족한다. **자동 연쇄를 넣지 마라** — 연쇄는 "한 번의 apply 가 파일과 DB 를 동시에 바꾼다"는 뜻이고, 실패 시 부분 적용 상태가 생긴다.

## D-5 (신규 · 리더 실측에서 파생) — 프레임 오염 제거를 **구현에 강제**한다

`00_leader_context.md` §2-1-2 참조. 시뮬레이터가 초록 주차면 박스를 렌더하고 있었고, 그것이 도색선을 **덮고** 있었다(`1:2` 백색 2.47% → 초록 제거 후 4.49%).

**구현 필수 사항:**
1. 프레임 취득 직전 **`roi.show2d {visible:false}`** 를 호출한다. (`preset.setBoxVisible` 은 효과 없음 — 리더 실측)
2. 취득한 프레임의 **초록 픽셀 비율 가드**: `g>110 && g-r>55 && g-b>55` 인 픽셀이 **0.1% 초과면 채점 중단**하고 `D11_SYNTHETIC_CUE` 로 오염 보고. 통과로 세지 않는다.
3. 검출기는 **그레이스케일만** 쓴다. 색 채널 분기 코드가 있으면 실카 전이 불가로 간주해 거부한다.

**근거:** 초록 박스는 실카에 없는 합성 단서다. 여기에 의존하면 시뮬에서만 98% 가 나오고 마스터가 요구한 "실제 리얼 화면 98%" 는 구조적으로 불가능해진다. 이것은 성능 문제가 아니라 **평가 오염(evaluation contamination)** 이다.

## D-6 — 부재중 실행 범위

| 허용 | 금지 |
|---|---|
| 신규 파일 작성·유닛테스트·채점·오버레이 렌더 | **정본 `PtzCamRoi.json` 쓰기** |
