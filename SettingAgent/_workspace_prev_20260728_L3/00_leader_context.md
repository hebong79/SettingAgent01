# 00 리더 컨텍스트 — L3: 주차면 1개 드로잉 → 전 프리셋 바닥 ROI 자동 생성

작성: 2026-07-27 / 실행 모드: **B(goal/loop)** — 프롬프트가 `Goal:`/`Loop:`/`Requirements:` 구조라 B 확정.

## Goal
카메라당 **주차면 1개만 수동으로 그리면** 그 카메라의 **전 프리셋 전 슬롯 바닥 ROI가 자동 생성**된다.
산출 ROI는 **결정론적**이어야 한다(같은 입력 → 같은 출력, 해시 일치).

### ★ Loop 1 (왕복 복원) — **통과**
`PtzCamRoi.json` quad → GroundModel → **지면 미터 2D 격자로 압축** → 역투영 → 원본 quad 와 IoU:

| preset | 슬롯 | θ | 실측 스팬 | 평균 IoU |
|---|---|---|---|---|
| 1 | 7 | 90.00° | 5.000 × 2.500 m | **1.0000** |
| 2 | 4 | 90.00° | 5.000 × 2.500 m | **1.0000** |
| 3 | 2 | 90.00° | 2.500 × 5.000 m | **1.0000** |

**전체 13슬롯 평균 IoU = 1.0000 (최소 1.0000).** 기준 0.95 를 완전히 통과.
→ **손 드로잉 quad 는 지면 위에서 정확히 규칙 2.5×5.0m 격자다.** 설계 전제 성립.

> ⚠️ **정직한 한계**: 이 데이터는 Unity 시뮬레이터 생성분이라 격자가 **구조적으로 완벽**하다.
> 실제 도색 주차장은 이만큼 규칙적이지 않다. 실카 데이터로 재확인이 필요하며, IoU 1.0000 을
> "실카에서도 1.0" 으로 읽으면 안 된다. 이 검증이 말하는 것은 **파이프라인 수학이 무손실**이라는 것뿐이다.

### 리더 검증 중 드러난 함정 (구현 시 반드시 회피)
1. **격자 피치는 슬롯 폭(2.5m)이다** — 슬롯은 폭 방향으로 반복된다. 피치를 깊이(5.0m)로 잡으면
   인접 슬롯이 반칸씩 어긋나 **IoU 가 1/0 으로 교대**한다(실측: 평균 0.5714, 슬롯별 `1 0 1 0 1 0 1`).
2. **단일 행을 가정하지 말 것** — 프리셋이 다른 주차열을 볼 수 있다(preset 3 은 스팬 축이 뒤집혀 있다:
   `2.5×5.0` vs preset 1·2 의 `5.0×2.5`). 열 인덱스(피치 2.5)와 **행 인덱스(피치 5.0)를 각각** 잡아야 한다.
   단일 행 가정 시 preset 2 는 정확히 반폭(1.25m) 어긋나 **IoU 0.333** 이 나온다.
3. **폭/깊이 축 판정은 지면 실측 스팬으로** 한다(픽셀 길이 판정 금지 — `groundModel.ts §4-6` 과 동일 원칙).

## Loop (리더가 따를 절차)
1. ✅ **왕복 복원 IoU ≥ 0.95** — **완료·통과(1.0000)**
2. 격자 자료구조 + `gridToPixelQuads(grid, model)` 순수함수 → 유닛테스트 + **골든 해시 고정**
3. 부트스트랩(주차면 1개 → 카메라 상수 fovBaseV/d/θ/원점) → `crossPresetSimilarityChecks` 통과
   (dDevRel < 10%, bearingDevDeg < 8°)
4. 전 프리셋 자동 ROI 생성 → 자동 quad vs 파일 quad **평균 IoU ≥ 0.9**, 슬롯 개수 일치
5. 라우트 + 웹 미리보기(겹쳐보기·IoU 표시·승인 후 저장) → sharp 스샷 육안 확인

## 리더 결정 (2026-07-27, 설계 리뷰 후) — 3건 전부 승인

### D-1. 정본 = 격자(authored) → PtzCamRoi.json → slot_setup(파생) ✅ 승인
설계자가 **내 전제를 코드 근거로 정정했고, 리더가 직접 재확인함**:
- `slot_roi` 쓰기 지점은 저장소 전체에 **정확히 2곳**(`Finalizer.ts:286`, `roiDbLoad.ts:182`)이고 **둘 다 소스가 PtzCamRoi.json**.
- LLM 폴리곤은 `slot_roi` 를 **쓰지 않는다** — `FloorRoiReviewer.ts:95` 가 `void resolveFloorPolygon(...)`
  로 버리고("산출 폴리곤은 미영속·본 클래스는 미배선 잔존"), `index.ts:63` 에서 배선 제거됨,
  `web/app.js:87` 은 `FLOOR_ROI_USE_LLM=false` 고정.
- → **내가 Requirements 에 적은 "LLM vs 자동격자 충돌"은 실재하지 않는다.** 진짜 충돌은 파일 ROI vs 자동 격자다.
- 그리고 이건 취향이 아니라 **결정된다**: `Finalizer.persistSlotSetupFromPlace` 가 매 finalize 마다
  `replaceSlotSetup`(전량 교체)을 PtzCamRoi.json 소스로 호출하므로 — **자동 격자를 DB 에만 쓰면 다음
  finalize 에서 반드시 소멸한다.**
- 채택: 승인 시 **파일(PtzCamRoi.json)을 갱신**한다. DB 쓰기 신규 코드 0줄, `replaceSlotSetup` 호출자 증가 0.
  (Requirements 의 "replaceSlotSetup 취약성 가드"는 이 구조로 **원천 회피**된다.)

### D-2. 신규 수학 = 프리셋 불변 지면 2D 좌표계 1건만 ✅ 승인
`GroundModel` 의 `n,d` 는 **프리셋별 카메라 좌표계** 값이라 격자를 카메라 좌표에 두면 프리셋을 건널 수 없다.
**리더의 Loop 1 은 프리셋 *내부* 왕복이었다** — 프리셋 간 이식은 검증하지 않았다(내 검증의 사각지대, 설계자가 지적).
다리는 기존 `slotBearingDeg`(`groundModel.ts:416`)의 역: 원점 = 카메라 나딜(`d·n`, 세계 고정점),
축 = pan 보정 기저 `e1/e2`. 약 40줄, `project.ts` 벡터 헬퍼 재사용.
`groundModel.ts`/`project.ts`/`types.ts`/`floorRoi.ts`/`Finalizer.ts`/`SqliteStore.ts`/`core.js` **변경 0줄**.

### D-3. Loop 3 성공기준 교체 — 홀드아웃 대조 ✅ 승인 (리더가 기준을 바꿈)
**내가 준 Loop 3 기준(`crossPresetSimilarityChecks` 통과)은 항진명제다.** 자동 모델은 `d` 를 같은 상수에서
복사하고 방위도 같은 격자에서 나오므로 `dDevRel`·`bearingDevDeg` 가 **정의상 0** — 아무것도 검증하지 못한다.
교체 기준(설계자 제안, 채택): **홀드아웃 대조** — preset1 quad 1개로 부트스트랩 → preset2/3 의 auto 모델을
파일 유래 모델과 대조: `|Δd|/d < 10%`, `|Δtilt| < 1.0°`, `|Δf|/f < 5%`. 신규 검증기 0, 기존 임계 재사용.

부수 규약(승인):
- 자동 모델의 `metricErr=0`/`tiltErr=0` 은 **품질이 아니라 구성상 0** → `conf` 를 1.0 으로 채우지 않고
  정직성 issue 문구를 강제한다(강등 위장 금지 원칙).
- 승인 적용 시 **기존 파일의 슬롯 순서 보존**, 개수 불일치면 **적용 거부**(R-4).
  여기가 흔들리면 `slot_ptz.json`·센터링·artifact `globalIndex` 가 통째로 어긋난다.
